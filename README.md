# Такт — предиктор изменений движения транспорта

Локальный MVP системы раннего прогнозирования отклонений наземного транспорта от расписания
(контракт backend/ML — **1.1.0**).

Система принимает телематические данные, сопоставляет их с плановым расписанием, строит причинные признаки, рассчитывает прогноз на горизонте 10–15 минут и отображает состояние транспорта в диспетчерском интерфейсе.

Актуальные источники истины:

- `http://127.0.0.1:8000/openapi.json` — сгенерированный контракт backend;
- `http://127.0.0.1:8000/docs/swagger` — интерактивный Swagger с примерами;
- `dashboard/docs.html` — объяснение API для интегратора;
- `docs/sphinx/` — документация кода, собираемая при старте backend.

## Что делает проект

Основной сценарий работы:

```text
NDTP / HTTP telemetry
        │
        ▼
     Backend
        │
        ├── хранит историю движения
        ├── сопоставляет ТС с расписанием
        ├── определяет целевую остановку
        │
        ▼
    ML service
        │
        ├── строит признаки
        ├── запускает CatBoost
        └── возвращает прогноз
        │
        ▼
     Backend
        │
        ▼
    Dashboard
```

Система позволяет:

- принимать NDTP-телеметрию;
- работать с HTTP-телеметрией;
- прогнозировать изменение отклонения транспорта от расписания;
- оценивать риск опоздания;
- отображать транспорт на карте;
- следить за выбранным ТС в реальном времени;
- работать с очередью рейсов, требующих внимания;
- открывать карточку выбранного рейса в правой боковой панели;
- регистрировать указания диспетчера;
- просматривать журнал указаний по конкретному рейсу;
- выполнять what-if сценарий выпуска резервного ТС;
- управлять паузой custom/original NDTP-источников;
- воспроизводить исторические точки в режиме replay;
- просматривать Swagger/OpenAPI и Sphinx-документацию кода.

# ML-модель

В текущей версии используется CatBoost.

Модель строит признаки по:

- телеметрической истории;
- текущему состоянию ТС;
- расписанию;
- геометрии маршрута;
- временному положению относительно целевой остановки.

`tr_id` и `target_stop_id` не используются моделью как обучающие признаки.

Диагностический результат текущей версии:

```text
MAE модели:               78.25 с
Persistence baseline:     93.36 с
```

Оценка получена на размеченной test-части исторических данных.

Важно: в доступной выборке используется ограниченный исторический период, поэтому эта оценка не является полноценной оценкой качества на будущих датах.

Подробности:

```text
docs/ANALYSIS.md
```

Из корня репозитория:

```sh
python scripts/run_prototype.py
```

```text
docker compose up -d --build
```

и запустит сервисы ML, backend, dashboard, custom-emulator и оригинальный NDTP-образ:

```text
ml
backend
dashboard
```

выданного `ndtp-telemetry-emulator.tar`. Если образ не загружен, стек не может
создать обязательный официальный контур; самописный `custom-emulator` не является
его заменой.

```text

   ↓

   ↓

   ↓
обновление координат
   ↓
```

Кнопка:

```text

```

отключает автоматическое перемещение карты.

```text

```

также отключает режим слежения и показывает общую картину.

При выборе другого ТС слежение автоматически переключается на него.

# What-if: выпуск резервного ТС

После выбора рейса доступен сценарий:

```text
Выпустить резервное ТС
```

Он вызывает:

```http
POST /api/what-if
```

Сценарий:

- выбирает линию;
- выбирает текущий плановый сегмент выбранного ТС;
- считает ограниченное снижение текущего и прогнозного отклонения на линии;
- добавляет виртуальное резервное ТС на карту;
- ведёт пунктирный сценарный трек до целевой остановки;
- возвращает эффект отдельно для основного и резервного ТС;
- не изменяет реальное расписание;
- не отправляет команду во внешний транспортный контур.

Это прозрачная what-if эвристика поддержки решения, а не новый ML-прогноз.

# Административный интерфейс

Адрес:

```text
http://127.0.0.1:8080/admin
```

Административный интерфейс позволяет:

- создавать профили диспетчеров;
- назначать рейсы;
- выбирать доступные ТС;
- видеть разницу между `custom-emulator` и внешним оригинальным NDTP-образом;

Сценарная симуляция намеренно убрана из интерфейса: она создавала синтетические события, не являясь физической моделью движения. Для прототипа проверка выполняется реальными NDTP-потоками, а совместимые simulation endpoint'ы оставлены только в API-документации.

При первом входе в рабочее место дашборд просит выбрать тестовую локальную учётную запись. Это демонстрационный выбор профиля, а не парольная аутентификация; выбранный профиль подписывает локальные указания и определяет назначения рейсов.

Данные сохраняются в:

```text
state/dispatcher.db
```

# NDTP-эмуляции и честность источника

Основной источник prototype — контейнер:

```text
custom-emulator
```

запускает собственную NDTP Nav00 эмуляцию из `dataset/validate`.

Он:

- создаёт корректные NDTP-пакеты;
- вычисляет CRC16/Modbus;
- устанавливает TCP-соединение с backend;
- отправляет позиции нескольких транспортных средств;
- перемещает ТС по плановым траекториям.

По умолчанию используется:

```text
NDTP_HOST=backend
NDTP_PORT=9201
EMULATOR_INTERVAL_S=3
EMULATOR_MAX_VEHICLES=0
```

`0` означает использование всех доступных ТС, для которых есть необходимые данные.

В карточке ТС источник не скрывается: для этого потока отображается `custom-emulator → NDTP Nav00 → CRC → backend → расписание → 102 causal-признака → V5`. Оригинальный образ остаётся отдельным внешним контейнером; его генерация управляется через предусмотренный `/api/config`, а сам контейнер по-прежнему принадлежит Docker Compose.

Оригинальный образ с пустым `cells` по своей спецификации генерирует синтетические GPS-координаты около Москвы и немного сдвигает их от тика к тику; REST-конфиг образа не умеет задавать маршрут. Поэтому backend действительно принимает обязательный оригинальный NDTP-поток, декодирует CRC/Nav00 и сохраняет исходные `raw_lon/raw_lat`, но для рабочей карты и сопоставления остановок использует непрерывную интерполяцию по плановой геометрии (`position_adjusted=true`). Это не скрытая замена источника: `telemetry_source=ndtp_nav00`, `position_origin=planned_route_projection`, а raw-координаты доступны для аудита. Так карта не телепортируется по синтетической траектории образа и не выдаёт её за фактический маршрут.

Если один из 13 оригинальных units ещё не успел прислать первый пакет, он не исчезает: `/api/state` показывает его как `source=waiting_for_live` в начале маршрута без выдуманного прогноза. После первого валидного NDTP-пакета карточка становится live.

В дашборде и `/admin` есть отдельные кнопки «Пауза» и «Пуск» для `custom-emulator` и оригинального NDTP, а также общий переключатель. Управлять потоками может любой выбранный рабочий профиль. `POST /api/admin/emulators/all/pause` дополнительно блокирует приём новых NDTP-событий backend. Backend при старте и при первом запросе статуса автоматически исправляет частичный конфиг оригинального образа до 13 расписанных устройств; после этого все 13 получают `autoGenerate=true` (вместе с 13 custom это максимум 26 ТС в картине). `units` в статусе означает настроенные устройства, а `waiting_for_live` — только те, от которых ещё не пришёл первый пакет. Это пауза потока, а не удаление контейнера.

Целевая остановка прогноза и ближайшая плановая остановка на карте — разные поля. Backend проецирует каждую валидную координату на сегмент плановой траектории и интерполирует ожидаемое время: `current_deviation_s` меняется по мере движения. `prediction_s` относится к будущей целевой остановке и не должен читаться как копия текущих секунд. Если модель обещает физически нереальное восстановление за 10–15 минут, backend ограничивает коррекцию, выставляет `prediction_adjusted=true` и пересчитывает интервал/риск; это явно видно в API и карточке. В карточке дополнительно показываются `previous_stop_time` и `next_stop_time`: это расчётное прохождение/ETA по плановой траектории, а не подтверждение фактической остановки. Для custom-emulator плановый ход привязан к первой подтверждённой позиции, поэтому «текущее» и «прогноз» относятся к одному проходу маршрута; прогноз всё равно смотрит на целевую остановку через 10–15 минут. Это оценка положения, а не факт прибытия; `reason` — наблюдаемый сигнал, `reason_explanation` — его расшифровка, причина отклонения всегда остаётся рабочей гипотезой.

# Работа с NDTP

Backend проверяет:

- длину пакета;
- signature;
- CRC;
- допустимость координат;
- порядок событий.

Поддерживаются:

- фрагментированные TCP-пакеты;
- несколько NDTP-сообщений в одном соединении;
- повторные события;
- опоздавшие события.

Более старое событие не должно перезаписывать более новое состояние.

# Replay

Для исторического воспроизведения используется режим:

```text
replay
```

Переключение режима:

```http
POST /api/mode
```

Пример:

```json
{
  "mode": "replay"
}
```

Следующая историческая точка:

```http
POST /api/replay/step
```

Replay используется для:

- тестирования;
- воспроизводимости;
- проверки модели;
- интеграционного QA.

# Live-режим

Режим:

```json
{
  "mode": "live"
}
```

используется для поступающей телеметрии.

Live-прогноз рассчитывается только если существует первая плановая остановка в окне:

```text
T + 10 минут < target <= T + 15 минут
```

Если подходящей остановки нет, система не должна выдавать новый live-прогноз только ради заполнения интерфейса.

# Ограничения MVP

Текущая система является демонстрационным локальным прототипом.

Она не включает полноценные production-возможности:

- SSO;
- JWT;
- production RBAC;
- внешний канал связи с водителем;
- подтверждение доставки команд;
- полноценный дорожный map matching;
- интеграцию с реальной транспортной инфраструктурой;
- production monitoring;
- SLA;
- отказоустойчивое хранилище потокового состояния.

---

# Хранение состояния

Оперативное состояние транспорта в основном хранится в памяти backend.

После рестарта могут быть потеряны:

```text
live history
текущие прогнозы
runtime state
```

При этом SQLite используется для более долговечных данных:

```text
профили диспетчеров
назначения рейсов
история симуляций
журнал указаний
```

Файл:

```text
state/dispatcher.db
```

# Демонстрация для жюри

Рекомендуемый сценарий:

1. Запустить:

```sh
python scripts/run_prototype.py
```

2. Открыть:

```text
http://127.0.0.1:8080/
```

3. Выбрать диспетчера.

4. Выбрать ТС на карте или в таблице.

5. Проверить:
   - прогноз;
   - риск;
   - целевую остановку;
   - live-позицию;
   - слежение карты.

6. Открыть:

```text
Журнал указаний по рейсу
```

7. Зарегистрировать тестовое указание.

8. Выполнить what-if сценарий резервного ТС.

9. Открыть административный интерфейс:

```text
http://127.0.0.1:8080/admin
```

10. Выбрать «Источники данных», если нужно поставить custom или original поток на паузу.

11. Открыть Sphinx:

```text
http://127.0.0.1:8080/code/
```

12. При необходимости открыть Swagger:

```text
http://127.0.0.1:8000/docs/swagger
```

# Важное замечание

Система предназначена для демонстрации подхода к раннему обнаружению отклонений движения транспорта.

Прогноз и риск являются вспомогательными сигналами для диспетчера и не должны интерпретироваться как автоматически установленная причина задержки или как команда транспортному средству.
