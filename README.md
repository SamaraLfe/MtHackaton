# Такт — предиктор изменений движения транспорта

Локальный MVP для задания «Предиктор изменений в графике движения городского
транспорта»: приём NDTP, отдельный ML-сервис, API и диспетчерский дашборд.
Backend/ML API: версия 1.1.0. Документ актуализирован 26 сентября 2026 года.

## Соответствие заданию

| Требование | Реализация и границы |
| --- | --- |
| Backend, ML и BI в Docker | `backend/`, `ml/`, `dashboard/`; взаимодействие по HTTP, запуск через Compose. |
| Python 3.12+, CatBoost, PyTorch | Python 3.12 в Docker; CatBoost V5.1 — рабочая модель, PyTorch — сравнительная модель в обучении. Ансамбль/Transformer не реализован. |
| Поток NDTP | TCP 9201: Nav00, CRC, фрагментация, обработка повторов и опоздавших событий. Работают оригинальный образ и собственный эмулятор. |
| Горизонт 10–15 минут | Первая плановая остановка строго в `(T+600, T+900]`. Без подходящей цели прогноз отсутствует; окно не расширяется. |
| Прогноз и ошибка | Прогноз отклонения, split-conformal интервал, эмпирический риск задержки >120 с; MAE на историческом test. |
| Паттерны сбоя | Скорость, тренд, простой, свежесть GPS. Причина — гипотеза, а не доказательство пробки, неисправности или посадки пассажиров. |
| Карта и алерты | Плановые траектории, позиции, очередь внимания, карточки и статусы рейсов. Полноценного дорожного графа и подтверждённых route_id нет. |
| Надёжность и latency | Последняя известная позиция при обрыве, критическое внимание к потере связи, readiness, runtime-метрики и скрипт проверки. |
| Документация | Руководство API, Swagger/OpenAPI, ReDoc и Sphinx из docstrings. |

Рабочий горизонт относится к **плановому времени контрольной остановки**.
Он не доказывает предупреждение за 10–15 минут до любого фактического сбоя.
Источника реального текущего расписания и подтверждённых событий дверей в
рабочем контуре пока нет. Эмуляторы используют исторический план со сдвигом.

## Запуск

Нужны Docker с Compose и Python 3.12+ для запуска управляющего скрипта.
Из корня проекта загрузите предоставленный организаторами образ:

```sh
docker load -i /path/to/ndtp-telemetry-emulator.tar
python scripts/run_prototype.py
```

На macOS/Linux вместо `python` может потребоваться `python3`.
Compose ожидает имя образа `ndtp-telemetry-emulator:1.0`; архив не скачивается
автоматически. Датасет и модель должны находиться в `dataset/` и `artifacts/`.
Скрипт выполняет `docker compose up -d --build` и запускает пять сервисов:
`ml`, `backend`, `dashboard`, `custom-emulator`, `emulator`.

| Адрес | Назначение |
| --- | --- |
| http://localhost:8080/ | Диспетчерская |
| http://localhost:8080/admin | Кабинеты, назначения и источники |
| http://localhost:8080/docs | Подробное руководство API |
| http://localhost:8000/docs/swagger | Swagger backend |
| http://localhost:8000/redoc | ReDoc |
| http://localhost:8000/openapi.json | Живой OpenAPI |
| http://localhost:8080/code/ | Sphinx |
| http://localhost:8000/health/ready | Проверка зависимостей |
| http://localhost:8000/api/observability | Runtime-метрики |

NDTP: `localhost:9201`. API оригинального эмулятора: `localhost:18080`,
собственного: `localhost:18081`. ML доступен внутри Compose по `http://ml:8001`.
Порты опубликованы только на loopback. Остановка: `docker compose down`.

В Docker устанавливаются `requirements.txt` и `requirements-docs.txt`.
`scripts/start_backend.py` собирает Sphinx перед запуском Uvicorn.
Если сборка документации не удалась, backend запускается с предупреждением;
поэтому перед сдачей нужна отдельная строгая проверка документации.

## Инструкция для жюри

1. Запустите стек и убедитесь, что `/health/ready` возвращает `200`.
2. Откройте диспетчерскую, выберите профиль и нажмите «Продолжить».
   Крестик, Escape, «Отмена» и клик вне окна закрывают выбор без применения.
   Это локальный выбор рабочего места, без паролей и SSO.
3. В live поступают пакеты двух NDTP-источников. Панель «Источники данных»
   позволяет управлять потоком; в карточке указано происхождение позиции.
4. Откройте ТС через карту, очередь внимания или таблицу. Карточка содержит
   начало/конец траектории, предыдущую/следующую остановку с расчётным временем,
   прогноз на контрольной точке, плановое и ожидаемое прибытие, свежесть позиции.
   Все отображаемые часы — МСК. Расчётные времена не подтверждают фактическое прибытие.
5. В «Почему так и откуда данные» доступны сигнал, телеметрия, текущая оценка
   отклонения, риск и время расчёта. «Сейчас» — не второй прогноз.
6. Проверьте указание диспетчера и журнал. Указания сохраняются в SQLite,
   но внешний канал доставки водителю не подключён.
7. Рассчитайте what-if выпуска резерва. Виртуальное ТС и его путь —
   иллюстративный сценарий; реальный выпуск и расписание не меняются.
8. В `/admin` можно управлять кабинетами и назначениями рейсов.
9. Для исторического прогона выполните запросы ниже. Режим общий для клиентов:

```sh
curl -sS -X POST http://localhost:8000/api/mode \
  -H 'Content-Type: application/json' -d '{"mode":"replay"}'
curl -sS -X POST http://localhost:8000/api/replay/step
curl -sS http://localhost:8000/api/metrics
# Вернуться к потоку; переключение сбрасывает оперативную историю
curl -sS -X POST http://localhost:8000/api/mode \
  -H 'Content-Type: application/json' -d '{"mode":"live"}'
```

### Что означает отсутствие оценки

| Статус | Поведение |
| --- | --- |
| Выход не подтверждён | Ни одного пакета текущего прогона; строка остаётся в таблице, ТС не считается активным. Отсутствие пакетов не доказывает, что водитель не выехал. |
| Нет связи · критично | На активном рейсе нет пакетов дольше `LIVE_STALE_S` (по умолчанию 15 с). Красный уровень, приоритет в очереди внимания, последняя позиция сохранена, прогноз очищен. |
| Нет контрольной точки | Пакеты приходят, но в строгом окне 10–15 минут нет остановки. Рейс продолжается. |
| Рейс завершён | Достигнут конец финального сегмента (доля ≥0,995, до конечной ≤30 м). ТС уходит с активной карты и счётчика, остаётся в таблице. Геометрический критерий прототипа. |
| Поток приостановлен | Общая пауза приёма оператором; ложная тревога связи не создаётся. |

API-поля: `trip_status`, `on_route`, `attention_level`, `status_label`,
`telemetry_age_s`, `route_start_stop`, `route_end_stop`. Критическая потеря
связи не является вероятностью опоздания: `late_probability=null`.

## Математика, качество и источники

CatBoost V5.1 использует 102 признака; `tr_id` и `target_stop_id` исключены.
История ограничена моментом T. Прогноз — отклонение в секундах: плюс означает
опоздание, минус — раннее прибытие. ETA = плановое время + `prediction_s`.
Backend не ограничивает разницу с текущей оценкой произвольной константой.

Данные из `artifacts/metrics.json` (353 исторические test-точки):

| Показатель | Значение |
| --- | --- |
| MAE V5.1 | 78,25 с |
| MAE persistence | 93,36 с |
| Покрытие интервала на test | 97,73% при номинальном 90% |
| Радиус интервала | 292,73 с |
| Batch inference | 3,00 мс на 353 точки в сохранённом замере; не end-to-end latency |

Ограниченный исторический период не подтверждает качество на будущих датах
или синтетическом потоке. [Разбор математики](docs/forecast-audit.md),
[аналитика модели](docs/ANALYSIS.md).

Собственный эмулятор интерполирует движение по плану. У оригинального образа
случайный GPS заменяется плановой интерполяцией: `position_adjusted=true`,
исходные `raw_lon/raw_lat` сохраняются. Это явно синтетическая позиция.
Backend восстанавливает конфигурацию оригинальных устройств; наличие
настроенного unit не гарантирует получение первого пакета.

## Проверка и артефакты сдачи

Для локального Python-окружения:

```sh
python -m venv .venv
# Активируйте .venv способом вашей ОС
python -m pip install -r requirements.txt -r requirements-docs.txt
python -m pytest -q
python scripts/verify_running.py --target docker
```

`verify_running.py` обращается к запущенному localhost-стенду, временно
переключает его в replay, проверяет 151 точку, горизонт, конечность прогнозов,
схему/идентификаторы submission, readiness, runtime-метрики и NDTP с
фрагментацией/ошибочным CRC. При успешном завершении возвращает исходный режим.
Это проверка контракта, не подтверждение MAE на скрытых validate-метках.
Отчёт: `artifacts/verification.json`; `VERIFICATION_OUTPUT` меняет путь записи.
`artifacts/` внутри backend-контейнера смонтирован read-only: при запуске
скрипта там задайте `VERIFICATION_OUTPUT=/tmp/verification.json`.

Для сдачи нужны:

- `artifacts/submission_v5.csv`: 151 строка, разделитель `;`, поля `sample_id;prediction`;
- ссылка на репозиторий с Compose и этим README;
- инструкция демонстрации выше;
- ссылки на API и Sphinx;
- сведения о latency из отчёта проверки с указанием условий замера.

Сохранённые замеры не являются SLA. Полный нагрузочный тест, реальные двери,
актуальное производственное расписание, дорожный map matching, SSO/RBAC и
внешняя доставка водителю остаются за рамками текущего MVP.
[План интеграций](docs/production-readiness.md).

## API и Sphinx

Руководство `/docs` объясняет поля и сценарии. Swagger `/docs/swagger` выполняет
настоящие запросы к состоянию стенда; `/openapi.json` — живой контракт.
Снимки контракта: `docs/openapi-backend.json`, `docs/openapi-ml.json`.

```sh
python scripts/export_openapi.py
python -m sphinx -b html docs/sphinx docs/_build/html -W --keep-going
```

Sphinx: `docs/_build/html/index.html`; сборка не хранится в Git. Для экспорта
OpenAPI можно задать `STATE_DIR` на временный каталог: скрипт запускает lifespan
приложения и открывает NDTP-порт, поэтому не запускайте его на занятом 9201
(используйте отдельный контейнер или `NDTP_PORT=0`).

Без Docker `python scripts/run_local.py` запускает только ML и backend:
панель на 8000, ML на 8001. Эмуляторы и Sphinx нужно запустить/собрать отдельно.
Для повторного обучения: `python -m ml.train --data dataset --out artifacts`.
Обучение перезаписывает артефакты; для обычного запуска оно не требуется.

## Хранение и структура

В памяти процесса: телеметрия, позиции, прогнозы, runtime-счётчики. В SQLite
`state/dispatcher.db`: профили, назначения, указания и legacy-запуски симуляций.
При рестарте память очищается; база сохраняется в bind mount `state/`.
Несколько backend-воркеров не синхронизируют оперативное состояние.

- `backend/` — API, NDTP, сопоставление, состояния рейсов;
- `ml/` — признаки, обучение и инференс;
- `emulator/` — собственный NDTP-источник;
- `dashboard/` — диспетчерская, админка и API-руководство;
- `scripts/` — запуск, экспорт и проверка;
- `tests/` — проверки математических и API-контрактов;
- `dataset/`, `artifacts/`, `docs/` — данные, модель и документация.
