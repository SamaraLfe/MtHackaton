# «Такт» — ранний прогноз отклонений городского транспорта

«Такт» — локальный прототип диспетчерской системы, которая принимает поток
телеметрии, сопоставляет транспорт с плановым расписанием и прогнозирует
отклонение на первой контрольной остановке в строгом окне **T+10…T+15 минут**.
Положительное значение прогноза означает опоздание, отрицательное — опережение.

Решение соответствует требуемому разделению на три самостоятельных модуля:

- **backend** — NDTP/HTTP-приём, расписание, оперативное состояние и API;
- **ML** — построение 60 причинных GPS-признаков и CatBoost-инференс;
- **dashboard** — карта, очередь внимания и карточка рейса.

Полный стенд собирается Docker Compose. Контракт backend/ML — **1.1.0**.

### Запуск без официального образа

Все три обязательных модуля и собственный NDTP-источник можно запустить без
закрытого образа организаторов и без установки Python на хост:

```sh
docker compose up -d --build ml backend dashboard custom-emulator
docker compose ps
curl --fail http://127.0.0.1:8000/health/ready
```

Откройте http://127.0.0.1:8080/ и выберите dispatcher-02. Официальный источник
в этом варианте недоступен; custom-поток и replay работают. Для полного стенда
загрузите официальный образ и используйте обычный запуск ниже. Первый build
дольше последующих: устанавливаются ML-зависимости и собирается Sphinx.

### Диагностика запуска

```sh
docker compose logs --tail=100 backend ml custom-emulator
docker compose restart backend
docker compose down
```

Перезапуск backend очищает live-историю и тикеты; профили и audit-журналы
остаются в bind-каталоге state/. Не запускайте несколько backend workers:
оперативное состояние принадлежит одному процессу. При занятых портах
8000/8080/9201/18080/18081 остановите другой стенд либо согласованно измените
Compose и клиентские адреса. Если /code/ недоступен, проверьте в логах сборку
Sphinx: старт backend допускается даже после ошибки документации.

|---|---:|
| Модель | CatBoost champion-b4b, direct delay |
| Число признаков | 60 |
| Score платформы, сообщённый для b4b636b | **1,00000** |
| MAE на выданной test-части | 62,09 с |
| Persistence baseline | 93,36 с |
| Улучшение к baseline | 33,49% |
| Покрытие 90% интервала на test | 90,37% |
| Радиус 90% интервала | 129,69 с |
| Чистый batch-инференс 353 строк | около 4–7 мс |

| Submission | 151 строка, без пропусков |

Метрики сохранены в `artifacts/metrics.json`, интеграционная проверка — в
`artifacts/verification.json`. Это ретроспективная оценка на ограниченной
раздаче, а не заявление о промышленном качестве на будущих днях. Платформенный
score и локальный MAE нельзя сравнивать напрямую: score нормируется скрытыми
`mae_zero` и `MAE_TARGET` и обрезается сверху на единице.

```text

Custom NDTP emulator ────┼── TCP :9201 ──► Backend :8000
POST /api/telemetry ─────┘                    │
                                              ├── расписание и map matching
                                              ├── оперативное состояние
                                              ├── SQLite: профили/назначения/указания
                                              │
                                              └── POST /predict_v5
                                                       │
                                                       ▼
                                                   ML :8001
                                                       │
                                                       ▼
Dashboard :8080 ◄──────────── REST/API ───── прогноз, риск, интервал
```

Backend владеет оперативной историей и выбирает целевую остановку. ML-сервис
не хранит состояние транспорта: он получает точки, истории и расписания одним
пакетом и возвращает прогнозы в том же порядке. Dashboard не содержит
бизнес-логики расчёта — он отображает контракт backend.

## Семантика прогноза

### Что именно предсказывается

Для момента `T` выбирается первая по плановому времени остановка, где:

```text
600 < target_time_begin - T <= 900 секунд
```

Результат:

```text
prediction_s = ожидаемое прибытие - плановое прибытие
```

- `prediction_s > 0` — ожидаемое опоздание;
- `prediction_s < 0` — ожидаемое прибытие раньше плана;
- `prediction_s = null` — надёжного прогноза сейчас нет.

Окно не расширяется. Если в нём нет плановой остановки, транспорт остаётся в
операционной картине со статусом «Нет контрольной точки», но прогноз не
подменяется ближайшей остановкой вне горизонта.

### Текущее отклонение и прогноз — разные величины

`current_deviation_s` оценивает положение **сейчас**. Координата проецируется
на текущий плановый сегмент, его плановое время интерполируется, после чего:

```text
current_deviation_s = event_time - expected_position_time
```

`prediction_s` относится к будущей контрольной остановке через 10–15 минут.
Поэтому эти числа могут различаться. Backend не обрезает текущее отклонение и
не сдвигает ответ V5 эвристической константой: прогноз, интервал и риск
остаются результатом модели и сохранённой калибровки.

### Интервал и риск

- `lower_s` / `upper_s` — эмпирический интервал по остаткам выданного test;
- `late_probability` — эмпирическая вероятность отклонения более 120 с;
- уровни интерфейса: `<35%` — низкий, `35–70%` — средний, `>=70%` — высокий.

Ширина интервала показывает неопределённость, но не доказывает причинность.
Поля `reason` и `reason_explanation` — наблюдаемый сигнал для проверки. При
отсутствии размеченных причин `reason_is_hypothesis=true`.

Подробный аудит вычислений: `docs/forecast-audit.md`.

## Статусы рейса и связи

Наличие прогноза не используется как признак начала или завершения рейса.

| `trip_status` | Значение |
|---|---|
| `not_started` | первый пакет текущего прохода ещё не получен; выход на линию не подтверждён |
| `active` | есть принятая телеметрия, ТС участвует в live-картине |
| `completed` | ТС достигло конца последнего планового сегмента; с активной карты снимается |

Если активное ТС не передаёт пакеты дольше `LIVE_STALE_S` (по умолчанию 15 с),
оно получает `attention_level=critical`, уровень риска `high`, последняя
позиция сохраняется, а устаревший прогноз скрывается. Намеренная пауза потока
показывается отдельно и не считается аварией связи.

`previous_stop_time` и `next_stop_time` — расчётные времена прохождения
соседних плановых точек. Это не подтверждение двери, валидатора или фактической
остановки.

### Общая остановка телеметрии

Если весь поток отсутствует `LIVE_FALLBACK_S` (60 с по умолчанию) или приём
приостановлен оператором, `/api/state` отдаёт исторический резерв:
`state.mode=replay`, `source_mode=live`, `fallback_mode=historical`.
Внутренний режим остаётся live. Архивные прогнозы отмечены
`source=historical_fallback`, `degraded=true`; `stale=false` у такой строки
не означает свежую оценку. Последняя live-позиция сохраняется при наличии.
ТС без архивной записи показываются без прогноза с `level=unknown` и
`attention_level=critical`. После снятия паузы новые пакеты возвращают
оперативную картину. Это отдельный режим от критической потери связи с одним ТС.

## Интерфейс диспетчера

При входе предлагается выбрать локальный тестовый профиль. Это демонстрация
рабочих кабинетов, а не production-аутентификация.

Основной экран показывает:

- очередь рейсов, отсортированную по критичности и риску;
- live-карту и плановые линии;
- источник, свежесть и статус связи;
- прогноз и интервал для выбранной контрольной остановки;
- предыдущую/следующую плановую точку с расчётным временем;
- раскрываемую диагностику текущего отклонения и происхождения координаты;
- журнал указаний выбранному ТС.

Выбор ТС в списке или на карте синхронизирован: карта приближается к маркеру и
продолжает следовать за ним, пока оператор не отключит слежение. Завершённые и
не вышедшие на линию рейсы остаются в таблице, но не засоряют активную карту.

Локальные профили:

- `admin-01` — открывает административный экран;
- `dispatcher-01` — маршрутный диспетчер с частью парка;
- `dispatcher-02` — «Диспетчер №2 (все ТС)», старший диспетчер со всем парком
  по умолчанию.

Администратор может создавать/удалять профили и полностью заменять список их
назначений. Любой выбранный профиль может приостанавливать и возобновлять
потоки эмуляторов для удобства демонстрации.

## Источники телеметрии

### Оригинальный NDTP-эмулятор

Оригинальный образ обязателен по условию. Backend через его REST config API
настраивает все 13 исходных `unit_id`; частичная старая конфигурация
восстанавливается до полного списка. После остановки конфигурация сохраняется,
поэтому повторный запуск возвращает те же устройства.

Пустой `cells` в выданном образе генерирует синтетические GPS-координаты, не
связанные с маршрутом. Для честного отображения backend сохраняет их в
`raw_lon/raw_lat`, ставит `position_adjusted=true` и использует
детерминированную интерполяцию по плановой траектории для рабочих `lon/lat`.
Это явно синтетическая позиция, а не наблюдение реального автобуса.

### Собственный эмулятор

`custom-emulator` создаёт отдельные копии 13 ТС и движет их между плановыми
точками. Идентификаторы смещены, чтобы не смешивать два источника. В штатной
конфигурации одновременно возможно до **26 ТС**: 13 оригинальных и 13 custom.

По умолчанию custom-копии независимо чередуют обычное движение, замедления,
остановки на 75–210 секунд и восстановление темпа. Это реальные изменения
генерируемых координат и скорости: риск рассчитывает прежняя ML-модель, без
подмены прогнозов. Первые инциденты начинаются через 20–55 секунд после запуска;
выход в жёлтую/красную зону зависит от расписания и накопленного отставания.
`EMULATOR_CHAOS=0` отключает инциденты, `EMULATOR_CHAOS_SEED=42` задаёт
воспроизводимый сценарий. Ручная debug-скорость приоритетнее хаотичного режима.
Изолированная проверка пяти минут движения с настоящей V5-моделью:
`python scripts/verify_chaos.py` (в окружении с зависимостями проекта).

### Управление

Статус и кнопки паузы/запуска доступны на dashboard и через:

```text
GET  /api/admin/emulators
POST /api/admin/emulators/{custom-emulator|official-emulator|all}/{pause|resume|stop}
```

«Работает» означает, что генерация включена, как и у оригинального источника;
короткое переподключение после запуска не меняет этот статус на `unknown`.
Фактическое NDTP-соединение custom-потока отдельно видно в `details.connected`.
Окно потоков закрывается крестиком справа сверху, Escape или кликом снаружи.

В replay источник в интерфейсе помечается как архивный. Архивная позиция не
выдаётся за live-пакет.

## Replay и submission

Replay последовательно проходит `dataset/validate/points.csv`. На каждом шаге
используются только строки телеметрии с временем не позднее `T`.

```text
POST /api/mode          {"mode":"replay"}
POST /api/replay/step   {}
```

Готовые файлы:

- `artifacts/submission.csv` — единственный canonical submission;
- формат UTF-8, разделитель `;`, колонки `sample_id;prediction`;
- 151 уникальная строка — по одной на каждую validate-точку.

Validate не содержит истинных ответов. Они не восстанавливаются из test или
других файлов.

## What-if резервного ТС

При прогнозе задержки от 3 минут резерв мгновенно появляется на остановке
около середины оставшегося пути. Сценарий возвращает компенсацию по остановкам,
сценарную вероятность пользы и решение по настраиваемым порогам `policy`.
Прогноз основного автобуса и показатели других маршрутов не изменяются.
Формулы, единицы измерения и пороги описаны в [бизнес-метриках](docs/business-metrics.md).

Это аналитический **what-if**: он не меняет live-расписание, не отправляет
команду водителю и не запускает транспорт физически. Для подтверждённого
решения используется `POST /api/reserve-dispatches`: он проходит guardrails и
сохраняет заявку в локальный integration outbox. Коэффициент эффекта —
эвристика прототипа, а не результат повторного ML-инференса.

## Центр действий диспетчера

`GET /api/action-center?dispatcher_id=...` показывает только действия, которые
зарегистрировал этот диспетчер. Назначение на тот же рейс другому сотруднику не
даёт доступа к его карточкам. Для пары «диспетчер + ТС» существует один
стабильный кейс: повторная попытка обновляет его, меняет `attempt_id` и
увеличивает `revision`, а не создаёт визуальный дубль.

Тикеты хранятся только в памяти backend (SQLite TEMP с `temp_store=MEMORY`),
не в файле БД. Каждый перезапуск backend начинает пустую сессию; открытые
вкладки видят общие тикеты своего диспетчера. F5 их не сбрасывает. Профили,
назначения и отдельный audit-журнал команд продолжают храниться на диске.
При обновлении удаляется старая дисковая таблица тикетов, но не эти журналы.

Указание водителю проходит цикл: `pending` («Отправляем водителю») →
`executing` («Исполняется») → `completed_success` («Закрыт») → удаление.
Ожидание приёма и недоставленные тикеты серые, исполнение синее, закрытие зелёное.
Зелёный тикет сохраняется 15 секунд от момента нового прогноза, подтвердившего
выход из зоны риска, затем удаляется полностью. Повторный опрос/новый риск
не продлевают срок и не возвращают закрытый тикет в исполнение. Очистка работает
даже без браузера или при остановленной телеметрии.

Демо-кнопка подтверждает приём и через тот же debug-оверлей повышает скорость
**только выбранного custom-ТС**: `min(130, max(30, speed × 1.5, speed + 15))`
км/ч, с учётом текущей ручной скорости. Повторный callback не ускоряет второй раз.
Оверлей можно сбросить кнопкой внизу карточки или перезапуском эмулятора.
Для оригинального потока демо по-прежнему подтверждает только приём.
Прогноз искусственно не меняется: результат зависит от новых координат и ML.
Закрытие требует нового прогноза после приёма: ТС ранее было в жёлтой/красной
зоне, а теперь стало зелёным (`level=low`, риск <35%). Данные должны быть
свежими, live, с активным рейсом и валидным прогнозом; архивные/устаревшие
наблюдения не закрывают тикет. Проверка выполняется при поступлении телеметрии,
даже без открытого браузера. Улучшения в секундах недостаточно, пока зона риска
остаётся жёлтой. Повторный callback, новый риск и перезапуск не восстанавливают
удалённый тикет; старая попытка не может затронуть новую.

Командный audit-журнал хранится отдельно: в нём остаются команда, подтверждение
и `completed` с доказательством закрытия. Для будущей интеграции предусмотрен
`POST /api/driver-commands/{id}/acknowledge`; настоящий канал водителя и защита
callback в production пока не подключены.

Для выпуска резерва сохранён отдельный демонстрационный результат компенсации,
не меняющий прогноз основного ТС. Успешная карточка видна 15 секунд, после чего
также удаляется из таблицы тикетов. Неподтверждённая за 15 минут доставка даёт
`not_delivered`. При старте очищаются все тикеты прошлой сессии, но не журналы
команд и выпуска резерва.
Заблокированное guardrail действие остаётся в audit-журнале, но не считается
выполненной попыткой и не попадает в центр результатов.

## Модель и обучение

Поставляемая модель `champion-b4b` воспроизводит лучший submission из коммита
`b4b636b` и строит признаки из:

- текущего отклонения и горизонта;
- календарного времени;
- свежести и валидности GPS;
- скорости, доли остановок и прямого перемещения в окнах 1/3/5/10/15 минут;
- направления последнего валидного пакета и расстояния до целевой остановки.

`tr_id` и `target_stop_id` исключены из обучающих признаков. Будущая
телеметрия после `T` не используется. CatBoost напрямую прогнозирует
`target_delay_s`; текущее отклонение `cur_dev_s` входит в признаки, но не
прибавляется к ответу повторно. Модель использует 500 деревьев глубины 6,
MAE-loss, `learning_rate=0.04` и `l2_leaf_reg=5`. Переобучение из исходных CSV
воспроизводит все 151 прогноза лучшего submission без расхождений. Связь с
score `1,00000` отмечена как сообщённый результат коммита `b4b636b`, а не как
вывод из локального MAE.

Переобучение:

```sh
python -m ml.train --data dataset --out artifacts
```

Ограничения оценки:

- доступен только один исторический день;
- официальный test пересекается с train по ТС и календарному дню;
- interval coverage на будущем дне не гарантирован;
- причин задержек, дорожного трафика, погоды и состояний дверей в раздаче нет.

Полный анализ: `docs/ANALYSIS.md`.

## Проверка решения

Частота live-пересчёта: текущее отклонение обновляется на каждом принятом
GPS-пакете, V5 — также на каждом обычном пакете (около 3 секунд при текущих
эмуляторах). `LIVE_FORECAST_INTERVAL_S=1` ограничивает слишком частые запросы
одного ТС; `0` разрешает прогноз на каждом пакете без ограничения. Новый пакет
и изменение целевой остановки не ждут отдельного фонового таймера.
Экран опрашивает состояние через 1 секунду после завершения предыдущего
запроса; расчёт действий карточки кэшируется на 3 секунды, статическая
геометрия — на 60 секунд. Второго цикла опроса нет.

При сбое ML действует общий `ML_RETRY_INTERVAL_S=5`: координаты и отклонение
продолжают обновляться, но повторные сетевые тайм-ауты не задерживают весь парк.
Сетевой timeout 2 секунды и порог потери связи 15 секунд сохранены: это не
интервалы пересчёта. Активные параметры доступны в `/api/observability`.

Математический аудит, исправления, численные результаты и ограничения:
[`docs/MATH_AUDIT.md`](docs/MATH_AUDIT.md).

### Автоматические тесты

```sh
python -m pytest -q
node --test tests/test_dispatcher_polling.mjs
```

Они проверяют причинность, строгий горизонт, feature schema, API, NDTP/CRC,
работу эмулятора, профили, what-if и жизненный цикл рейса.

### Проверка запущенного Docker-контура

Это изменяющая состояние проверка: временно переключает общий backend в
replay, подаёт тестовые NDTP-кадры и записывает отчёт. Выполняйте на тестовом
стенде без активной работы диспетчера. При успешном завершении возвращает
исходный режим; при ошибке верните live через POST /api/mode вручную.

```sh
python scripts/verify_running.py --target docker
```

Параметр `--target` только маркирует отчёт, а не выбирает адрес подключения.
Скрипт всегда обращается к localhost:8000/9201 и требует Python-зависимостей
проекта. В контейнере backend они уже установлены:

```sh
docker compose exec -e VERIFICATION_OUTPUT=/app/state/verification-docker.json backend python scripts/verify_running.py --target docker
```

В Compose artifacts/ подключён read-only, поэтому контейнерный отчёт пишется
в state/verification-docker.json. Архивный отчёт в artifacts/ не перезаписывается.

Проверка подтверждает:

- readiness и observability;
- полный replay 151 точек;
- схему и покрытие submission;
- строгий горизонт каждого replay-прогноза;
- приём фрагментированного NDTP-кадра;
- отклонение кадра с неверным CRC;
- latency replay-запросов.

### Сборка документации кода

Sphinx собирается автоматически в `scripts/start_backend.py` перед запуском
Uvicorn. Ручная строгая проверка:

```sh
python -m sphinx -W -b html docs/sphinx docs/_build/html
```

## Данные и хранение состояния

- `dataset/` — train/test/validate, планы, labels и спецификация NDTP;
- `artifacts/` — единственная копия модели, schema, метрик, submission и verification;
- live-история, позиции и прогнозы — память одного backend-процесса;
- профили, назначения, указания и история тестовых запусков — SQLite в `state/`;
- оригинальные raw GPS-точки сохраняются в оперативной истории для аудита.

После перезапуска live-история исчезает. Текущая авторизация — локальный выбор
профиля без пароля. Это осознанные границы MVP, не production-модель
безопасности или отказоустойчивости.

## Структура полного прототипа

```text
backend/       FastAPI, NDTP, состояние, расписание и what-if
ml/            признаки, обучение, CatBoost и inference API
dashboard/     диспетчерская, админка, карта и руководство API
emulator/      собственный управляемый NDTP-источник
dataset/       входные данные и спецификация
artifacts/     модель, метрики, submission и отчёт проверки
docs/          анализ, OpenAPI, Sphinx и аудит прогнозов
scripts/       запуск, экспорт контрактов и runtime-проверка
tests/         unit и integration-контракты
compose.yaml   полный локальный стенд
```

## Назначение веток

В профильных ветках намеренно хранится только их зона ответственности:

| Ветка | Содержимое |
|---|---|
| `prototype` | полный запускаемый прототип |
| `main` | обзор решения и исходное задание |
| `backend` | только `backend/` и его README |
| `ml` | `ml/`, модельные артефакты и ML README |
| `dashboard` | только интерфейс и его README |
| `data` | только `dataset/` и описание данных |
| `integration` | Docker/config, скрипты, проверки и снимки документации |

Так ветки не создают конкурирующих копий чужой бизнес-логики, а `prototype`
остаётся единственной интеграционной точкой демонстрации.

## Сценарий демонстрации для жюри

Короткая самостоятельная инструкция со всеми адресами и командами находится в
[`docs/jury-guide.md`](docs/jury-guide.md). Описание состава решения и ссылки на материалы приведены в [`docs/submission-form.md`](docs/submission-form.md).

1. Загрузить официальный образ и выполнить `python scripts/run_prototype.py`.
2. Открыть http://127.0.0.1:8080/ и выбрать профиль диспетчера.
3. Показать 13 оригинальных и 13 собственных ТС, источник и свежесть пакета.
4. Выбрать активное ТС: карта приблизится и начнёт следовать за ним.
5. Открыть карточку: прогноз, интервал, контрольная остановка и ETA.
6. Остановить один поток и показать отдельные статусы паузы/потери связи.
7. Запустить what-if резерва и показать виртуальный маркер и расчёт «до/после».
8. Отправить указание по ТС в зоне риска, подтвердить демо-приём и показать
   «Исполняется» и повышение debug-скорости custom-ТС. После выхода ТС в зелёную
   зону тикет станет зелёным «Закрыт», затем исчезнет через 15 секунд.
9. Переключиться в replay и показать явную архивную маркировку.
10. Открыть Swagger и Sphinx по ссылкам выше.
11. Выполнить `python scripts/verify_running.py --target docker` и показать отчёт.

## Что ещё нужно для production

- актуальное расписание на день эксплуатации и официальные номера маршрутов;
- проверенный дорожный map matching вместо ломаной по остановкам;
- размеченные фактические прибытия и причины инцидентов;
- backtest по будущим дням и мониторинг drift/качества после запуска;
- постоянное хранилище телеметрии и горизонтальное масштабирование;
- очередь сообщений с backpressure и идемпотентностью;
- полноценная аутентификация, роли, аудит и секреты;
- реальный канал доставки указаний водителю;
- нагрузочные и fault-injection тесты.

До выполнения этих пунктов «Такт» следует считать проверяемым локальным MVP,
а не готовой системой управления городским транспортом.
