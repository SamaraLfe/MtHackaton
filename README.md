# Такт — предиктор изменений движения транспорта

Локальный MVP системы раннего прогнозирования отклонений наземного транспорта от расписания.

Система принимает телематические данные, сопоставляет их с плановым расписанием, строит причинные признаки, рассчитывает прогноз на горизонте 10–15 минут и отображает состояние транспорта в диспетчерском интерфейсе.

## Что делает проект

Основной сценарий работы:

```text
NDTP / HTTP telemetry
        │
        ▼
     Backend
        │
        ├── хранит историю движения
        ├── сопоставляет ТС с расписанием
        ├── определяет целевую остановку
        │
        ▼
    ML service
        │
        ├── строит признаки
        ├── запускает CatBoost
        └── возвращает прогноз
        │
        ▼
     Backend
        │
        ▼
    Dashboard
```

Система позволяет:

- принимать NDTP-телеметрию;
- работать с HTTP-телеметрией;
- прогнозировать изменение отклонения транспорта от расписания;
- оценивать риск опоздания;
- отображать транспорт на карте;
- следить за выбранным ТС в реальном времени;
- работать с очередью рейсов, требующих внимания;
- открывать карточку выбранного рейса в правой боковой панели;
- регистрировать указания диспетчера;
- просматривать журнал указаний по конкретному рейсу;
- выполнять what-if сценарий выпуска резервного ТС;
- запускать тестовые сценарии через административный интерфейс;
- воспроизводить исторические точки в режиме replay;
- просматривать Swagger/OpenAPI и Sphinx-документацию кода.

# ML-модель

В текущей версии используется CatBoost.

Модель строит признаки по:

- телеметрической истории;
- текущему состоянию ТС;
- расписанию;
- геометрии маршрута;
- временному положению относительно целевой остановки.

`tr_id` и `target_stop_id` не используются моделью как обучающие признаки.

Диагностический результат текущей версии:

```text
MAE модели:               78.25 с
Persistence baseline:     93.36 с
```

Оценка получена на размеченной test-части исторических данных.

Важно: в доступной выборке используется ограниченный исторический период, поэтому эта оценка не является полноценной оценкой качества на будущих датах.

Подробности:

```text
docs/ANALYSIS.md
```

## Выбор транспорта

ТС можно выбрать:

- нажатием на маркер на карте;
- нажатием на строку в таблице;
- через очередь внимания.

После выбора справа открывается карточка рейса.

На desktop карточка не перекрывает основной интерфейс — рабочая область сдвигается влево.

В карточке отображаются:

- текущий статус;
- прогноз отклонения;
- риск;
- целевая остановка;
- предыдущая остановка;
- следующая остановка;
- текущий участок;
- время позиции;
- диагностические признаки;
- источник данных;
- действия диспетчера;
- журнал указаний.

# Следование карты за ТС

При выборе ТС карта автоматически включает режим слежения.

Алгоритм:

```text
выбор ТС
   ↓
центрирование карты
   ↓
follow mode
   ↓
новая телеметрия
   ↓
обновление координат
   ↓
карта перемещается за выбранным ТС
```

Кнопка:

```text
Не следить
```

отключает автоматическое перемещение карты.

Кнопка:

```text
Показать все
```

также отключает режим слежения и показывает общую картину.

При выборе другого ТС слежение автоматически переключается на него.

# Указания диспетчера

Диспетчер может зарегистрировать одно из безопасных действий:

```text
contact
accelerate_safely
maintain
slow_down_safely
```

Пример:

```text
Связаться и уточнить
```

или:

```text
Предложить безопасно сократить отставание
```

Указания сохраняются в локальную SQLite-базу.

Важно: текущий MVP не отправляет реальные команды водителю.

Это локальная аудируемая очередь для демонстрации будущей интеграции.

# What-if: выпуск резервного ТС

После выбора рейса доступен сценарий:

```text
Выпустить резервное ТС
```

Он вызывает:

```http
POST /api/what-if
```

Сценарий:

- выбирает линию;
- добавляет виртуальное резервное ТС;
- рассчитывает изменение уровня риска;
- показывает резерв на карте;
- добавляет сценарный трек;
- не изменяет реальное расписание;
- не отправляет команду во внешний транспортный контур.

Это инструмент поддержки решения диспетчера.

Адрес:

```text

```

Административный интерфейс позволяет:

- создавать профили диспетчеров;

- запускать тестовые сценарии;
- просматривать статус сценариев;
- просматривать историю запусков;
- отменять активные сценарии.
- видеть разницу между `custom-emulator` и внешним оригинальным NDTP-образом;
- ставить custom-поток или весь приём новых событий на паузу и возобновлять его.

При первом входе в рабочее место дашборд просит выбрать тестовую локальную учётную запись. Это демонстрационный выбор профиля, а не парольная аутентификация; выбранный профиль подписывает локальные указания и определяет назначения рейсов.

Данные сохраняются в:


# NDTP-эмуляции и честность источника

Основной источник prototype — контейнер:

```text
custom-emulator
```

запускает собственную NDTP Nav00 эмуляцию из `dataset/validate`.

Он:

- создаёт корректные NDTP-пакеты;
- вычисляет CRC16/Modbus;
- устанавливает TCP-соединение с backend;
- отправляет позиции нескольких транспортных средств;
- перемещает ТС по плановым траекториям.

По умолчанию используется:

```text
NDTP_HOST=backend
NDTP_PORT=9201
EMULATOR_INTERVAL_S=3
EMULATOR_MAX_VEHICLES=0
```

`0` означает использование всех доступных ТС, для которых есть необходимые данные.

В карточке ТС источник не скрывается: для этого потока отображается `custom-emulator → NDTP Nav00 → CRC → backend → расписание → 102 causal-признака → V5`. Оригинальный образ остаётся отдельным внешним контейнером; его генерация управляется через предусмотренный `/api/config`, а сам контейнер по-прежнему принадлежит Docker Compose.

Кнопка «Поставить поток на паузу» в `/admin` вызывает `POST /api/admin/emulators/all/pause`: custom-emulator получает pause, backend перестаёт принимать новые NDTP-события, а активные тестовые симуляции отменяются перед следующим событием. Возобновление выполняется обратной кнопкой. Это пауза потока, а не удаление контейнера.

Плановая остановка в карточке не считается фактом прибытия. Backend отмечает её только при близкой координате и скорости ниже 5 км/ч; адрес остановки сам по себе не доказывает причину отклонения. Для каждого ТС текст «Рабочая гипотеза, не подтверждённая причина» остаётся явным — даже когда модель показывает 0 секунд.

# Работа с NDTP

Backend проверяет:

- длину пакета;
- signature;
- CRC;
- допустимость координат;
- порядок событий.

Поддерживаются:

- фрагментированные TCP-пакеты;
- несколько NDTP-сообщений в одном соединении;
- повторные события;
- опоздавшие события.

Более старое событие не должно перезаписывать более новое состояние.

# Replay

Для исторического воспроизведения используется режим:

```text
replay
```

Переключение режима:

```http
POST /api/mode
```

Пример:

```json
{
  "mode": "replay"
}
```

Следующая историческая точка:

```http
POST /api/replay/step
```

Replay используется для:

- тестирования;
- воспроизводимости;
- проверки модели;
- интеграционного QA.

---

# Live-режим

Режим:

```json
{
  "mode": "live"
}
```

используется для поступающей телеметрии.

Live-прогноз рассчитывается только если существует первая плановая остановка в окне:

```text
T + 10 минут < target <= T + 15 минут
```

Если подходящей остановки нет, система не должна выдавать новый live-прогноз только ради заполнения интерфейса.
