# Такт — предиктор изменений движения транспорта

Рабочий локальный MVP: прогноз задержки на первой плановой остановке через строго более 10 и не более 15 минут, causal NDTP-поток, отдельные ML/API-модули и диспетчерский интерфейс.

**Результат V5.1:** CatBoost на 102 признаках (телеметрические окна + признаки расписания и геометрии), диагностический MAE `78,25 с` против persistence baseline `93,36 с` на 353 test-точках. `tr_id` и `target_stop_id` исключены. Модель обучена на хронологической development-части, а интервалы и риск рассчитаны на отдельной calibration-части. Доступен только один исторический день, поэтому это не оценка качества на будущих датах. [Аналитика и ограничения](docs/ANALYSIS.md).

## Быстрый запуск Docker

В поставку включены CSV, готовая модель и встроенный NDTP-эмулятор. Скрипт собирает локальные Docker-образы и запускает поток по всем известным ТС из validate-расписания — без загрузки приватного образа и без GitHub credentials:

```sh
python scripts/run_prototype.py
```

- Дашборд: http://localhost:8080
- Руководство API: http://localhost:8080/docs (также http://localhost:8000/docs)
- Интерактивный Swagger backend: http://localhost:8000/docs/swagger
- NDTP: TCP localhost:9201
- ML доступен внутри сети Compose по `http://ml:8001`.

Четыре контейнера: ml, backend, dashboard и emulator. Dashboard через nginx проксирует API. Backend стартует в `live`, поэтому встроенный эмулятор сразу запускает контур NDTP → признаки → V5 → dashboard. Пока первый live-прогноз не готов, интерфейс явно показывает сохранённый архивный V5 fallback. Для остановки: `docker compose down`.

## Локальный запуск без Docker

Python 3.12+:

```sh
python -m venv .venv
```

Windows:

```powershell
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python scripts/run_local.py
```

Linux/macOS:

```sh
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/run_local.py
```

Дашборд: http://127.0.0.1:8000, ML: http://127.0.0.1:8001/docs. Ctrl+C завершает оба процесса. На исходном компьютере также можно запустить `start-local.ps1`: он использует подготовленные зависимости Codex, если нет `.venv`. Не запускайте вторую копию на занятых портах.

## Демонстрация для жюри

1. Открыть `http://localhost:8080/`. Диспетчер видит назначенные ему рейсы, состояние NDTP-потока и число live-прогнозов; fallback всегда помечен как архивный.
2. Открыть карточку ТС на карте или в таблице: видны прогноз, риск, предыдущая и следующая остановки, текущий участок и свежесть live-позиции.
3. Открыть `http://localhost:8080/admin`: создать кабинет диспетчера и назначить ему рейсы. Назначения сохраняются в локальной SQLite-базе `state/dispatcher.db`.
4. На административной странице запустить тестовый сценарий. Экран показывает статус, прогресс, принятые тестовые NDTP-события и эффект на прогноз до/после.
5. `GET /api/metrics` возвращает офлайн-оценку V5, `GET /api/state?dispatcher_id=…` — состояние закреплённых за диспетчером рейсов.
6. Live-прогноз рассчитывается только при наличии целевой плановой остановки строго в окне T+10…15 минут; иначе свежая позиция накладывается на отдельно помеченный архивный fallback.

Линии схемы соединяют плановые остановки ТС; это не дорожная карта и не официальная маршрутная сеть. Серый статус также появляется при устаревании прогноза на 120 секунд относительно часов соответствующего режима.

## Данные и обучение

Если CSV были удалены или получена новая раздача:

```sh
python scripts/extract_data.py /path/to/dataset.zip --out dataset
python -m ml.train --data dataset --out artifacts
python -m pytest -q
```

Папки `train`, `test`, `validate`, `labels` сохраняют исходные имена. Единая команда строит V5-признаки, подбирает число итераций CatBoost на хронологическом tuning-блоке, обучает финальную модель на development-блоке и калибрует её на последнем временном блоке. PyTorch L1 и persistence сохраняются как честные baselines. Идентификаторы ТС, ID остановки и фактические прибытия не используются как признаки. Все runtime-артефакты, метрики и оба submission-файла создаются одной командой.

Схема математики и ограничения в [ANALYSIS.md](docs/ANALYSIS.md). CSV-времена без timezone трактуются как UTC по проверке Unix-суффикса `sample_id`, UI отображает Europe/Moscow.

## NDTP-эмулятор и живой контур

`emulator/service.py` собирает корректные NDTP Nav00-кадры с CRC16/Modbus и открывает одно TCP-подключение к `backend:9201`. По умолчанию раз в 3 секунды отправляются позиции всех 13 ТС, для которых одновременно есть `unit_id` в `traffic.csv` и минимум две координаты в `schedule_plan.csv`. Каждое ТС плавно проходит вдоль упорядоченной плановой траектории с реалистичной скоростью и без скачков между остановками. Параметры локальной нагрузки задаются переменными Compose `EMULATOR_INTERVAL_S` и `EMULATOR_MAX_VEHICLES` (`0` — все доступные ТС).

Поток не меняет исторический fallback: свежая NDTP-координата накладывается на архивную карточку и карту как live-позиция, а архивный прогноз не выдаётся за прогноз текущего рейса. Пакет старше одного часа не получает live-маркировку. Для достоверного live-прогноза по-прежнему нужны расписание и фактические данные текущей даты.

Приёмник проверяет длину, signature, CRC16/Modbus со swap и значения координат. Сокеты допускают фрагментацию и несколько пакетов подряд. Повторные/опоздавшие события не перезаписывают новое состояние. Разрыв соединения не сбрасывает последнее состояние; его давность видна в UI. Поддержанные дополнительные типы ячеек перечислены в `backend/ndtp.py`; неизвестные сенсоры не интерпретируются как двери.

## API

Полное руководство с примерами, полями ответов и ошибками: `/docs`. Swagger для
проверки запросов: `/docs/swagger`, спецификация: `/openapi.json`. Руководство
учитывает профили диспетчеров, назначения рейсов, архивный снимок и
асинхронные симуляции текущей версии backend.

- `POST /api/telemetry` — массив до 1000 событий `{tr_id,event_time,lon,lat,speed,location_valid}`.
- `POST /api/predict` — `{tr_id,T,target_stop_id,target_time_begin,cur_dev_s}`; проверяется первая остановка планового окна, признаки строятся из принятой истории.
- `POST /api/replay/step` — следующий исторический прогноз.
- `POST /api/mode` — `{"mode":"live"}` или `{"mode":"replay"}`.
- `GET /api/state?dispatcher_id=…`, `/api/network`, `/api/metrics`, `/api/risk`, `/api/incidents`, `/health`, `/health/ready`, `/api/observability`.
- `POST /api/map-match` — сегмент плановой траектории, направление и расстояние до следующей остановки; без дорожного графа это не road map matching.
- `POST /api/what-if` — сценарий выпуска дополнительных ТС и снижения интервала.
- `GET /api/driver-commands?tr_id=…` — журнал указаний для выбранного ТС.
- `POST /api/driver-commands` — диспетчер регистрирует указание `contact`, `maintain`, `accelerate_safely` или `slow_down_safely`; команда видна в карточке ТС и имеет статус очереди интеграции.
- `GET /api/dispatchers`, `POST /api/admin/dispatchers`, `PUT /api/admin/dispatchers/{id}/assignments` — локальные кабинеты и назначения рейсов.
- `POST /api/admin/simulations`, `GET /api/admin/simulations?status=…&tr_id=…`, `GET /api/admin/simulations/{id}`, `POST /api/admin/simulations/{id}/cancel` — тестовая симуляция с жизненным циклом, отменой, историей SQLite, прогрессом, событиями и эффектом до/после. Старый `/api/admin/simulation` оставлен для совместимости.
- Админская панель: `http://localhost:8080/admin`. Это локальные управляемые кабинеты, а не production SSO/JWT.
- ML `POST /predict_v5` — основной endpoint V5: prediction point + causal NDTP history + schedule; `/health` сообщает загруженную модель. Устаревший `POST /predict` явно отвечает `410` при загруженной V5 вместо скрытой ошибки размерности.

Полный интеграционный контроль локальных сервисов: `python scripts/verify_running.py --target local`; Docker-контура: `python scripts/verify_running.py --target docker`. Проверка временно включает replay, проходит все 151 точки, проверяет submission, фрагментированный TCP-пакет и ошибочный CRC, затем возвращает исходный режим. Тип проверенного запуска явно записывается в `artifacts/verification.json`.

Сохранённые OpenAPI-спецификации находятся в `docs/`. Не публикуйте этот локальный MVP в интернет без добавления авторизации.

Подробный план перехода в рабочий контур, включая SSO, актуальное расписание,
дорожный map matching, связь с водителем, нагрузку и сдачу: [docs/production-readiness.md](docs/production-readiness.md).

## Документация кода (Sphinx)

Sphinx строит справочник по backend, NDTP, ML V5, обучению и скриптам из
docstrings. Зависимости документации отделены от runtime-образа:

```sh
python -m pip install -r requirements.txt -r requirements-docs.txt
python -m sphinx -b html docs/sphinx docs/_build/html -W --keep-going
```

Откройте `docs/_build/html/index.html`. На macOS/Linux можно выполнить
`make html` из `docs/sphinx`, на Windows — `docs\sphinx\make.bat html`.
Каталог `docs/_build/` игнорируется Git.

> Связь с водителем в текущем MVP — аудируемая локальная очередь диспетчерских указаний. Реальный радио-, телефонический или телематический канал не подключён: интерфейс прямо показывает этот статус и не заявляет о внешней доставке. Для промышленного применения нужны аутентификация диспетчера, интеграция с утверждённым каналом связи и подтверждение получения водителем.

## Структура

```text
ml/          признаки, обучение, статистика, инференс и ML API
backend/     NDTP, HTTP, replay, сопоставление с планом
emulator/    встроенный multi-vehicle NDTP Nav00-эмулятор для Docker QA
dashboard/   диспетчерский интерфейс, карта OpenStreetMap и административный контур
tests/       горизонт, утечки признаков, CRC, API, деградация
scripts/     извлечение данных и локальный запуск
artifacts/   готовая модель, submission и отчёты
docs/        анализ, источники, OpenAPI и PyDoc
dataset/     исходные CSV, без Docker tar эмулятора
```

При рестарте история потока теряется, но кабинеты диспетчеров, назначения, история тестовых симуляций и локальная очередь указаний водителю сохраняются в SQLite. Гарантии внешней доставки, полноценное сопоставление с дорогой, production-аутентификация и управление резервными ТС не входят в MVP.
