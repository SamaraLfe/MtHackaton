# Переход локального MVP в рабочий контур

Этот документ продолжает `NEXT_STEPS.md`. Он отделяет функции, уже
реализованные в репозитории, от интеграций, для которых нужен владелец
внешней системы, договорённый контракт и секреты. Ничего из перечисленного
ниже не следует объявлять подключённым до прохождения соответствующего шага.

## Что реализовано в этом репозитории

- `GET /health/ready` проверяет загруженные данные, SQLite, артефакты V5 и ML
  API; вернёт `503` с полем `checks`, если прогнозный контур не готов.
- `GET /api/observability` отдаёт bounded runtime-метрики: HTTP latency,
  счётчики ошибок, размер истории, очередь указаний и активные симуляции.
- `GET /api/state` возвращает до 100 валидных live-точек в `live_track`.
  Тестовые события имеют `simulated: true`; карта показывает реальный след
  голубым пунктиром, симуляцию — фиолетовым.
- `/api/map-match` сопоставляет положение с сегментом плановой траектории,
  показывает направление и расстояние до следующей остановки. Это ещё не
  дорожный map matching: в исходных данных нет графа дорог.
- Симуляции сохраняются в SQLite, имеют фильтруемую историю и отменяются
  через `POST /api/admin/simulations/{id}/cancel`.

## 1. SSO, роли и аудит

Владелец: команда IAM и владелец диспетчерской роли.

1. Выбрать провайдера OIDC/SAML и зарегистрировать отдельный production
   client с redirect URL панели.
2. Зафиксировать claims: неизменяемый `sub`, отображаемое имя и набор ролей
   `dispatcher`, `senior_dispatcher`, `administrator`, `auditor`.
3. На backend проверять подпись, issuer, audience, expiration и nonce токена;
   получать роль только из проверенных claims, а не из тела HTTP-запроса.
4. Перенести диспетчеров, назначения, revocation и аудит из локального SQLite
   в управляемую БД. В аудите хранить actor, действие, объект, время,
   request-id и результат без access token и персональных секретов.
5. Настроить срок серверной сессии, refresh, logout, блокировку после
   согласованного числа неудачных входов и процедуру разблокировки.
6. Прогнать сценарии: доступ только к назначенным ТС, запрет админских
   операций диспетчеру, отзыв доступа, параллельные сессии, audit export.

Критерий готовности: все административные endpoints требуют проверенную
серверную identity; `role` и `dispatcher_id` больше не принимаются как
доказательство прав.

## 2. Расписание текущей даты

Владелец: поставщик планирования движения.

1. Согласовать источник: API, SFTP/CSV или очередь; получить схему,
   часовой пояс, SLA публикации и способ идентификации рейса.
2. Ввести стабильные `trip_id`, `vehicle_id` и `route_id`; связать их с
   текущим `tr_id` через версионируемую таблицу соответствия.
3. Проверять полноту, монотонность остановок, координаты, дубликаты и дату
   плана перед публикацией. Хранить `schedule_version`, `published_at` и TTL.
4. Загружать новый план атомарно. Если план текущей даты отсутствует или TTL
   истёк, принимать live-координату как overlay, но возвращать прогноз
   `unknown` с причиной `current_schedule_unavailable`.
5. Сверить 10–15-минутное окно с диспетчерским источником на наборе реальных
   рейсов и включить alert при просрочке плана.

Критерий готовности: каждый live-прогноз ссылается на `schedule_version`
текущей даты; устаревший план не может породить прогноз.

## 3. Дорожный map matching

Владелец: GIS-команда или лицензированный провайдер графа дорог.

1. Получить дорожный граф или API с условиями хранения и использования.
2. Импортировать полилинии рейсов с направлением, segment ID и допустимым
   направлением движения; не подменять их прямыми между остановками.
3. Сопоставлять GPS с кандидатом на сегменте с учётом расстояния, курса,
   скорости и предыдущего кандидата; хранить confidence и reason fallback.
4. Возвращать `road_graph_matched: true` только после успешного сопоставления
   и отдельно тестировать развязки, обратное направление и туннели.

## 4. Канал связи с водителем

Владелец: утверждённый оператор телефонии/рации/телематики.

1. Получить контракт отправки, идентификатор водителя/устройства, webhook
   delivery/read и правила хранения сообщений.
2. Локальный MVP уже сохраняет команды в SQLite outbox. Для production добавить idempotency key, фонового worker, передачу провайдеру и повтор только временных ошибок.
3. Обрабатывать webhook с проверкой подписи; состояния должны быть
   `queued`, `sent`, `delivered`, `read`, `failed`, а не только локальное
   `queued_for_integration`.
4. Показать в UI фактический delivery status и аудит. До этого текущая
   очередь остаётся явно локальной и не означает доставку водителю.

## 5. Мониторинг, нагрузка и сдача

1. Опросить `/health/ready` из оркестратора и `/api/observability` из
   коллектора; отправлять stdout-логи контейнеров в выбранное центральное
   хранилище с request-id на стороне ingress.
2. Задать SLO для E2E: время от NDTP event до обновления `/api/state`,
   p95/p99 HTTP и error rate. Добавить alert по readiness, ML failure,
   просроченному расписанию и росту очереди.
3. Запустить изолированный нагрузочный прогон несколькими ТС и фиксировать
   p50/p95/p99, потерянные/дублированные точки, использование CPU и памяти.
   Не запускать нагрузку в production без окна и лимитов.
4. Перед сдачей поднять локальный стек, дождаться `GET /health/ready`, затем
   выполнить `python scripts/verify_running.py`. Скрипт меняет режим replay,
   поэтому запускать его только на стенде проверки.
5. Проверить `artifacts/submission_v5.csv`, сохранить
   `artifacts/verification.json` и зафиксировать commit, timestamp, статус
   readiness и результат проверки в релизной записи.
