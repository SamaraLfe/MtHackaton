# Инструкция для жюри

Решение «Такт» запускается локально из ветки `prototype`. Три основных
модуля — ML-ядро, backend и BI-дашборд — собраны Docker Compose. Два
дополнительных сервиса подают тестовую телеметрию: официальный NDTP-образ и
встроенный маршрутный эмулятор.

## 1. Запуск

Требуются Docker с Compose, Python 3.12+ и выданный организаторами образ
`ndtp-telemetry-emulator:1.0`.

Если образ ещё не загружен:

```sh
docker load -i ndtp-telemetry-emulator.tar
docker image inspect ndtp-telemetry-emulator:1.0
```

Из корня репозитория:

```sh
python scripts/run_prototype.py
```

Скрипт выполняет `docker compose up -d --build` и ждёт готовности backend и
встроенного эмулятора. Успешный запуск заканчивается строкой
`Prototype is ready`.

## 2. Куда смотреть

| Ресурс | Адрес после запуска |
|---|---|
| BI-дашборд диспетчера | http://127.0.0.1:8080/ |
| Инструкция по API | http://127.0.0.1:8080/docs |
| Sphinx-документация кода | http://127.0.0.1:8080/code/ |
| Swagger UI | http://127.0.0.1:8000/docs/swagger |
| OpenAPI JSON | http://127.0.0.1:8000/openapi.json |
| Readiness | http://127.0.0.1:8000/health/ready |
| Runtime-метрики | http://127.0.0.1:8000/api/observability |
| Метрики модели | http://127.0.0.1:8000/api/metrics |

В дашборде выберите `dispatcher-02`: этот профиль видит весь тестовый парк.
Прогноз, интервал и риск находятся в таблице и карточке выбранного ТС. Рейсы,
которые требуют вмешательства, показаны в очереди внимания; следующие действия
и истёкшие интеграции — в центре действий.

## 3. Как подать поток NDTP

После запуска оба источника включаются автоматически:

- официальный `ndtp-telemetry-emulator:1.0` передаёт Nav00 в TCP
  `127.0.0.1:9201`;
- `custom-emulator` передаёт отдельные маршрутные ТС по тому же NDTP-входу.

Статус источников доступен в панели «Источники данных» и через
`GET /api/admin/emulators`. Потоки можно приостановить и снова запустить из
интерфейса. В штатной демонстрации видны до 26 ТС: 13 официальных и 13
собственных.

Backend проверяет CRC16, собирает фрагментированные TCP-кадры, отклоняет
повторы и неизвестные устройства. Исходная синтетическая координата
официального образа сохраняется как `raw_lon/raw_lat`; рабочая позиция явно
помечается `position_adjusted=true` и проецируется на плановую траекторию.

## 4. Как запустить исторический replay

Переключить backend в replay и выполнить один шаг можно через Swagger либо:

```sh
curl -X POST http://127.0.0.1:8000/api/mode \
  -H "Content-Type: application/json" \
  -d '{"mode":"replay"}'

curl -X POST http://127.0.0.1:8000/api/replay/step \
  -H "Content-Type: application/json" \
  -d '{}'
```

Каждый вызов `/api/replay/step` обрабатывает следующую точку
`dataset/validate/points.csv`, используя только телеметрию с временем не позже
момента прогноза. Дашборд явно помечает такой источник как архивный.

Полный прогон всех 151 точек, проверка submission, горизонта и NDTP:

```sh
python scripts/verify_running.py --target docker
```

Отчёт сохраняется в `artifacts/verification.json`.

## 5. Что показать на демонстрации

1. Открыть дашборд и выбрать `dispatcher-02`.
2. Показать live-карту, источник и свежесть телеметрии.
3. Открыть ТС: прогноз на T+10…15 минут, интервал, вероятность задержки и
   объяснение входных сигналов.
4. Показать очередь внимания и центр действий, сравнение пользы действий
   `benefit-v1`, guardrails и локальную реакцию водителя.
5. Запустить what-if резервного ТС и показать расчёт ETA, запаса времени и
   ожидаемого эффекта до регистрации выпуска.
6. Открыть Swagger, Sphinx и `/api/observability`.
7. Выполнить `python scripts/verify_running.py --target docker`.

## 6. Границы прототипа

Это проверяемый локальный MVP. Внешний канал связи с водителем и реальный выпуск
резерва не подключены: решения сохраняются в SQLite-outbox, а демонстрационная
реакция водителя моделируется отдельно. Live-история телеметрии хранится в
памяти процесса. Для production потребуются аутентификация, message broker,
постоянное хранилище телеметрии и проверка качества на будущих днях.
