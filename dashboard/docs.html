к понятному прогнозу

Такт помогает диспетчеру заранее увидеть отклонение транспорта от расписания. API принимает координаты и скорость, рассчитывает прогноз на ближайшие 10–15 минут и отдаёт данные для карты и очереди внимания.

HTTP + JSONМодель V5Локальный прототипLive / Replay

Это руководство объясняет, что делает каждый блок API, какие данные ему нужны и как трактовать результат. Начните с готового исторического прогона, затем переходите к приёму своего потока. Для проверки отдельных запросов есть интерактивный Swagger, для альтернативного просмотра схемы — ReDoc, а для генерации клиента — OpenAPI JSON. Снимок контракта обновляется командой python scripts/export_openapi.py.

Первый прогноз за три запроса

Предполагается, что backend и ML уже запущены с данными и моделью из репозитория. Для запуска используйте python scripts/run_prototype.py с Docker или python scripts/run_local.py в подготовленном Python-окружении. Подробная установка описана в README проекта.

Примеры ниже рассчитаны на Bash / zsh. В PowerShell используйте curl.exe и синтаксис переменных вашей оболочки. Для Docker выберите порт 8080; без Docker — 8000.

export TAKT_URL=http://localhost:8080
# Без Docker: export TAKT_URL=http://127.0.0.1:8000
curl -sS "$TAKT_URL/health"

Ответ {"status":"ok","mode":"replay"} означает, что backend доступен. Текущий режим может быть live, если его уже переключили в интерфейсе. Эта проверка не подтверждает доступность ML.

1. Начните исторический прогон

Replay использует готовые прогнозные точки и телеметрию из dataset/validate. Ни NDTP-эмулятор, ни ручная отправка координат для него не нужны.

Этот запрос сбрасывает состояние.

История телеметрии и последние прогнозы очищаются для всех открытых клиентов, даже если replay уже выбран. Выполняйте пример в своём демонстрационном окружении.

curl -sS -X POST "$TAKT_URL/api/mode" \
  -H 'Content-Type: application/json' \
  -d '{"mode":"replay"}'

Ожидаемый ответ содержит mode: "replay". В актуальной версии backend сразу восстанавливает архивный снимок: в /api/state уже есть последняя историческая запись по каждому ТС. Первый шаг replay очищает этот снимок и начинает последовательный прогон.

2. Рассчитайте следующую точку

curl -sS -X POST "$TAKT_URL/api/replay/step"

Ответ содержит done: false, объект prediction и index: 1. Внутри prediction проверьте prediction_s — отклонение в секундах, level — уровень внимания и degraded — использован ли резервный расчёт. При доступной V5 ожидается model: "v5" и degraded: false.

3. Прочитайте общее состояние

curl -sS "$TAKT_URL/api/state"

В vehicles находится текущая картина рейсов; эти же данные использует диспетчерская. Повторяйте второй шаг, чтобы продвигаться по историческим точкам. Когда получите done: true, прогон завершён; поля prediction в таком ответе уже нет.

Как устроен прогноз

Backend хранит историю отдельно для каждого транспортного средства. В момент T он ищет в расписании первую остановку, до планового прибытия на которую осталось строго больше 600 и не больше 900 секунд. Затем передаёт точку, историю до T и плановое расписание в ML-сервис. Будущая телеметрия для расчёта не используется.

Например, для T = 10:00 остановка в 10:10 не подходит, а в 10:15 подходит. Если в этом окне есть остановки в 10:12 и 10:14, целевой будет остановка в 10:12. Если несколько остановок имеют одно и то же первое время, ручной запрос допускает любую из них.

ПонятиеЧто означает
tr_idИдентификатор транспортного средства (ТС). Отдельного идентификатора официального маршрута в данных нет. В сводках «маршруты» группируются по этому же полю.
unit_idИдентификатор NDTP-устройства. Backend сопоставляет его с tr_id по датасету и настройке UNIT_MAP. HTTP-телеметрия сразу принимает tr_id.
TМомент, на который строится прогноз. Это время данных, которое в replay относится к историческому дню.
target_stop_idИдентификатор плановой остановки: поле tt_action_item_id расписания.
cur_dev_sЧисловой признак для V5: live-координата проецируется на ближайший сегмент плановых остановок, а время сегмента интерполируется. Если сопоставления нет, для входа модели используется 0, а в ответе честно возвращается current_deviation_s: null. Это оценка положения, не подтверждение прибытия.
prediction_sПрогноз отклонения на целевой остановке, а не время поездки до неё. 180 означает опоздание на 3 минуты; -60 — прибытие на минуту раньше.

Два источника — одно общее состояние

Replay обрабатывает по одной строке validate/points.csv за запрос. Для неё берётся историческая телеметрия последних 10 минут. Live реагирует на входящие события HTTP или NDTP и рассчитывает прогноз не чаще раза в 30 секунд времени событий для каждого ТС.

В live план переносится на московский календарный день входящего события. Это сдвиг исходного расписания, а не загрузка актуального плана перевозчика. Координата сопоставляется с плановой траекторией, поэтому карточка различает целевую остановку прогноза и ближайшую остановку на карте. Если геометрию сопоставить нельзя, current_deviation_s становится null, а не нулём.

СервисАдрес и назначение

Спецификация/openapi.json — актуальная схема backend; /docs/swagger — интерактивные запросы; /redoc — альтернативный просмотр схемы.
  • Формат. Тела HTTP-запросов — JSON с Content-Type: application/json. Успешный ответ — JSON и статус 200, кроме создания указания (201). GET не требует тела.
  • Время. Используйте ISO 8601, например 2026-01-06T03:35:00Z. Время без смещения трактуется как UTC; backend отображает нормализованное время в Europe/Moscow. 03:35Z и 06:35+03:00 — один момент.
  • Единицы. Отклонения, интервалы и горизонты — секунды; скорость — км/ч; расстояния — метры; координаты — градусы; вероятности — от 0 до 1. null означает отсутствие оценки, а не ноль.
  • Доступ. API локального MVP не использует ключи или сессии. dispatcher_id выбирает локальный профиль из SQLite, а role проверяет переданное значение; это не production-аутентификация.
  • Общее состояние. Режим, телеметрические буферы и очередь указаний общие для всех клиентов и теряются при перезапуске. Профили, назначения и история асинхронных симуляций сохраняются в SQLite. Вебсокетов нет: интерфейс опрашивает HTTP API.
  • Повторы. Idempotency-Key не реализован. Повтор replay продвинет прогон, повтор создания указания создаст ещё одну запись, повтор выбора режима снова очистит состояние.
Примеры и реальные данные.

Далее $TAKT_URL — адрес, заданный в быстром старте. Поля в JSON-примерах ответов могут быть сокращены; числовые оценки иллюстрируют формат и не обещают конкретный результат модели.

Как читать результат прогноза

Этот объект возвращает POST /api/predict. В replay он находится в поле prediction, а в GET /api/state — в массиве vehicles. Сначала проверяйте достоверность данных, затем уровень внимания и величину отклонения.

{
  "tr_id": 131672,
  "T": "2026-01-06T06:35:00+03:00",
  "target_stop_id": 53700172828,
  "target_time_begin": "2026-01-06T06:50:00+03:00",
  "horizon_s": 900,
  "prediction_s": 180,
  "lower_s": 75.2154988903,
  "upper_s": 284.7845011097,
  "late_probability": 0.7913914727,
  "level": "high",
  "model": "v5",
  "source": "historical_replay",
  "degraded": false,
  "stale": false,
  "reason": "Устойчивое отклонение от графика",
  "reason_is_hypothesis": true
}
ПоляКак использовать
tr_id, TОпределяют ТС и момент расчёта. В vehicles хранится только последнее значение для каждого ТС.
target_stop_id, target_time_begin, stop_addressКуда и на какое плановое время построен прогноз. Плановое время плюс prediction_s даёт прогнозируемое время прибытия.
horizon_s, horizon_fallbackРазница между плановым временем целевой остановки и T. Всегда 600 < horizon_s <= 900. При отсутствии остановки в этом окне прогноз не рассчитывается; поле horizon_fallback оставлено для совместимости и равно false.
prediction_sОтклонение в секундах на будущей целевой остановке: плюс — позднее плана, минус — раньше. Это не обязано совпадать с текущей оценкой положения.
prediction_s и current_deviation_sПрогноз V5 для целевой остановки и оценка отклонения по текущей позиции. Backend не ограничивает разницу между ними произвольной константой.
lower_s, upper_sГраницы эмпирического интервала отклонения. В текущем артефакте радиус около 129.69 с вокруг прогноза. Это оценка неопределённости, не гарантированные пределы.
late_probabilityЭмпирическая оценка риска опоздания более чем на 120 с по калибровочным остаткам V5. Это не подтверждённая причина и не гарантия вероятности на будущем дне.
levellow, medium, high или unknown. Правила ниже. Нельзя определять уровень только по величине prediction_s.
model, degradedВ штатном режиме v5 и false. При ошибке ML — persistence_fallback и true: прогноз равен текущему cur_dev_s, вероятность отсутствует.
staleИстина при отсутствии достоверного GPS или возрасте телеметрии больше 120 с на момент расчёта. /api/state дополнительно проверяет возраст самого прогноза.
current_deviation_s, deviation_estimatedТекущее отклонение и происхождение оценки. deviation_estimated: true — интерполяция по сегменту, false — медленная телеметрия у плановой точки с тем же live-сдвигом расписания; null означает, что координата не сопоставилась с планом, а не «0 секунд».
position_match, previous_stop_time, next_stop_timeСегмент плановой траектории, ближайшая/следующая плановая остановка, расстояние до неё и расчётные времена прохождения. Это геометрическое сопоставление и ETA, а не подтверждение остановки; фактический заезд без отдельного события не заявляется.
source, telemetry_source, position_adjusted, raw_lon, raw_latsource обозначает контекст расчёта: live, historical_replay или api. telemetry_source показывает путь живой координаты: custom_ndtp_nav00 — собственный custom-emulator, ndtp_nav00 — оригинальный Nav00 с проверкой CRC и разбором NDTP; http_json — событие POST /api/telemetry. Для оригинального образа position_adjusted=true означает, что синтетическая GPS-точка autoGenerate сохранена в raw_lon/raw_lat для аудита, а рабочие lon/lat маркера получают непрерывную точку на плановой траектории. У образа нет настройки маршрута в REST-конфиге, поэтому это необходимая граница прототипа, а не скрытая подмена источника.
reason, reason_explanation, reason_is_hypothesis, recommendationreason — наблюдаемый паттерн, reason_explanation — почему он выбран. reason_is_hypothesis=true всегда означает: причина не подтверждена событием, например низкая скорость сама по себе не доказывает пробку или поломку.
lon, lat, position_timeПоследняя подходящая позиция и её Unix-время в секундах. Координаты могут быть null; position_time — число, в отличие от строкового T.
featuresДиагностические признаки backend: скорость, возраст GPS, простой и другие значения. Это компактный набор полей для объяснения, а не полный вход модели из 60 признаков.
УровеньУсловие и смысл
lowРиск меньше 0.35 при пригодных данных. Наблюдать в обычном режиме.
mediumОт 0.35 включительно до 0.70. Включить ТС в очередь внимания.
highОт 0.70 включительно. Проверить ситуацию и доступность резерва.
unknownНедостаточно надёжных данных: сбой ML, устаревание, нет целевой остановки или подтверждённого отклонения. Это не «всё хорошо».
Не все записи содержат полный прогноз.

Если в live не нашлась остановка в нужном окне, запись содержит идентификатор, время, координаты, источник, level, reason и null вместо прогноза и вероятности. Поля цели, модели, интервала и признаков могут отсутствовать. Клиент должен это учитывать.

function describePrediction(item) {
  if (item.level === 'unknown' || item.prediction_s == null) {
    return item.reason || 'Недостаточно данных';
  }
  const seconds = Math.round(Math.abs(item.prediction_s));
  return item.prediction_s >= 0
    ? `Опоздание на ${seconds} с`
    : `Раньше плана на ${seconds} с`;
}

GET/healthBackend · состояние

Доступность сервиса

Самая простая проверка, что backend отвечает на HTTP-запросы. Используйте её перед интеграцией или в проверке доступности. Параметров нет.

curl -sS "$TAKT_URL/health"
{"status":"ok","mode":"replay"}

status сообщает о доступности backend, mode — о выбранном источнике. Даже при остановленном ML или отсутствии NDTP ответ может быть ok. Для этих случаев проверяйте счётчики и признаки деградации в состоянии.

GET/api/stateBackend · состояние

Состояние транспорта

Основной запрос для диспетчерского интерфейса. Возвращает архивный снимок каждого ТС, live-наложения, положение исторического прогона и диагностические счётчики. Необязательный query-параметр dispatcher_id оставляет только назначенные профилю рейсы; пагинации нет.

curl -sS "$TAKT_URL/api/state"
{
  "vehicles": [],
  "state": {"mode":"replay","clock":null,"index":0},
  "counters": {},
  "total_points": 151
}

vehicles содержит объекты прогноза. В replay используется source: "historical_v5": это сохранённый прогноз V5 для validate-набора. В live новая телеметрия заменяет архивную запись только после успешного прогноза; до этого интерфейс явно помечает резервные данные. state.clock — время последнего события или replay-точки, state.index — шаги прогона, total_points — размер validate-набора.

При чтении backend проверяет давность: если с T прошло больше 120 секунд, в ответе появляются stale: true, level: "unknown" и объяснение. В replay сравнение идёт с часами прогона, поэтому остановленный прогон не стареет вместе с реальными часами. Проверка меняет только копию ответа.

СчётчикЧто показывает
telemetry_rowsСколько новых событий добавлено в историю через ingest. Replay читает CSV напрямую и этот счётчик не увеличивает.
predictionsКоличество рассчитанных прогнозов, включая резервные.
last_inference_msДлительность последней попытки обращения backend к ML в миллисекундах; это не время обработки всего HTTP-запроса.
ml_failuresСколько раз backend перешёл на резервный прогноз после ошибки обращения к ML или разбора ответа.
late_or_duplicate_packetsСобытия с временем не новее последнего принятого для того же ТС.
ndtp_packets, ndtp_errors, ndtp_disconnectsОбработанные NDTP-пакеты, ошибки разбора и разрывы/окончания соединений.
unknown_units, invalid_eventsNDTP-события без сопоставленного ТС и события, не прошедшие последующую проверку.

Ключи счётчиков появляются по мере использования: отсутствующий счётчик в интерфейсе можно показывать как 0. Переключение режима не обнуляет накопленные счётчики.

GET/api/dispatchersBackend · рабочие места

Профили диспетчеров и назначения

Профиль определяет, какие рейсы показывает диспетчерская. Это локальный демонстрационный вход: парольных логинов, токенов и SSO здесь нет, при входе выбирается тестовая учётная запись. При первом запуске создаются admin-01, dispatcher-01 и старший «Диспетчер №2 (все ТС)» (dispatcher-02), которому по умолчанию назначен весь парк.

curl -sS "$TAKT_URL/api/dispatchers"
curl -sS "$TAKT_URL/api/dispatchers/dispatcher-01"
curl -sS "$TAKT_URL/api/state?dispatcher_id=dispatcher-01"

Первый запрос возвращает profiles; каждый профиль содержит id, name, login, role, status и assigned_tr_ids. Второй возвращает один профиль или 404. Третий фильтрует общую картину только назначенными tr_id; неизвестный профиль также даёт 404.

POST /api/admin/dispatchers

Создаёт профиль и возвращает 201. login должен быть уникален и содержать строчные латинские буквы, цифры, _ или -; пароль не задаётся.

curl -sS -X POST "$TAKT_URL/api/admin/dispatchers" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Диспетчер №03","login":"dispatcher03","role":"Маршрутный диспетчер"}'

PUT /api/admin/dispatchers/{dispatcher_id}/assignments

Полностью заменяет назначения профиля. Тело {"tr_ids":[]} снимает все назначения. Все идентификаторы должны присутствовать в текущем расписании; иначе ответ 422.

curl -sS -X PUT "$TAKT_URL/api/admin/dispatchers/dispatcher-01/assignments" \
  -H 'Content-Type: application/json' \
  -d '{"tr_ids":[131672]}'

DELETE /api/admin/dispatchers/{dispatcher_id}

Удаляет рабочий кабинет и его назначения. Сам администратор не удаляется; операцию подтверждает operator_id действующего администратора.

curl -sS -X DELETE "$TAKT_URL/api/admin/dispatchers/dispatcher-03" \
  -H 'Content-Type: application/json' \
  -d '{"operator_id":"admin-01"}'
POST/api/modeBackend · меняет состояние

Режимы live и replay

Выбирает, откуда берутся данные для автоматических прогнозов. Тело содержит обязательную строку mode: live или replay. Другое значение вернёт 422.

curl -sS -X POST "$TAKT_URL/api/mode" \
  -H 'Content-Type: application/json' \
  -d '{"mode":"live"}'
{"mode":"live","clock":null,"index":0}

Каждый вызов очищает историю телеметрии, сохранённые прогнозы, наблюдённые отклонения и таймеры прогноза. Индекс и часы сбрасываются; расписание восстанавливается из исходного шаблона. Очередь указаний и счётчики сохраняются.

Повторный выбор текущего режима тоже сбрасывает данные.

Не вызывайте этот метод перед каждым пакетом телеметрии. Выберите live один раз при осознанном запуске потока. Изменение сразу затрагивает других пользователей этого backend.

POST/api/replay/stepBackend · меняет состояние

Исторический прогон

Обрабатывает ровно одну следующую прогнозную точку из validate/points.csv. Тело запроса не нужно. Данные идут по времени T; для каждой точки выбирается история этого ТС за предыдущие 10 минут, затем результат сохраняется в общем состоянии.

curl -sS -X POST "$TAKT_URL/api/replay/step"

Пока точки есть, ответ содержит done: false, prediction, mode, clock и index. По завершении возвращается done: true вместе с режимом, часами и индексом, без prediction. Последние прогнозы остаются доступны через /api/state.

409 означает, что выбран live. 422 означает несоответствие точки активному расписанию. При недоступном ML шаг всё равно может завершиться с 200, но прогноз будет резервным: degraded: true.

Повтор — это следующий шаг.

После сетевого тайм-аута сначала прочитайте /api/state и проверьте index. Повтор запроса может продвинуть прогон ещё на одну точку.

POST/api/telemetryBackend · меняет состояние

Приём телеметрии

HTTP-вход для координат и скорости — удобен, если ваш источник не использует бинарный NDTP. Тело запроса — массив от 1 до 1000 событий. В одном массиве могут быть разные ТС; события каждого ТС передавайте по возрастанию времени.

ПолеТип и ограничениеНазначение
tr_idinteger, > 0, обязательноИдентификатор ТС, как в расписании.
event_timestring, обязательноВремя события; предпочтительно ISO 8601 с часовым поясом. Не более чем на 60 с впереди часов сервера.
lonnumber, −180…180, обязательноДолгота, градусы.
latnumber, −90…90, обязательноШирота, градусы.
speednumber, 0…130, обязательноСкорость в км/ч.
location_validboolean, по умолчанию trueМожно ли использовать GPS для признаков и положения. При false координаты и скорость всё равно должны пройти проверку полей.

Лишние поля, бесконечные и нечисловые значения отклоняются. В примере используется историческое событие, чтобы его время оставалось воспроизводимым. Это демонстрация формата, а не подключение актуального live-потока.

curl -sS -X POST "$TAKT_URL/api/telemetry" \
  -H 'Content-Type: application/json' \
  -d '[{
    "tr_id": 131672,
    "event_time": "2026-01-06T03:34:50Z",
    "lon": 37.60,
    "lat": 55.75,
    "speed": 25,
    "location_valid": true
  }]'
{"accepted":1}

accepted — число событий в прошедшем проверку пакете. Событие с временем меньше или равным последнему принятому для того же ТС будет пропущено, но всё равно входит в accepted. Фактический прирост истории виден по counters.telemetry_rows, повторы — по late_or_duplicate_packets.

Что происходит в live

Сначала выберите live через /api/mode, затем отправляйте свежие события из своего источника. Backend переносит план на день события, пытается наблюдать текущее отклонение на остановках и, если прошло хотя бы 30 секунд времени событий с предыдущей попытки, выбирает цель и запускает прогноз. Сам ответ /api/telemetry не содержит прогноз: прочитайте его через /api/state.

В replay HTTP-события добавляются в буфер для ручного /api/predict, но не запускают автоматический прогноз и не заменяют CSV-историю шага replay. В памяти хранится максимум 1000 событий на ТС.

422 возвращается при неверных полях, пустом/слишком большом массиве, некорректной дате или времени из будущего. Проверка всех временных меток выполняется до добавления пакета в буфер.

POST/api/predictBackend · сохраняет прогноз

Запрос прогноза для выбранной точки

Используйте, когда ваша интеграция сама задаёт момент расчёта, целевую остановку и текущее отклонение. Backend возьмёт ранее принятую историю этого ТС, проверит цель по активному расписанию и обратится к ML.

ПолеТипПравило
tr_idinteger > 0ТС, чья история и расписание используются.
TstringВремя расчёта; не более 60 с в будущем относительно сервера.
target_stop_idintegerОстановка с первым плановым временем в окне (T+10, T+15] минут.
target_time_beginstringПлановое время этой остановки. Допустимое расхождение с расписанием — не больше 1 с.
cur_dev_snumberИзвестное текущее отклонение в секундах, может быть отрицательным.

Все поля обязательны; дополнительные поля запрещены. Пример соответствует первой точке поставляемого validate-набора и требует исходного исторического расписания (режим replay после сброса). Предварительно отправьте историю через /api/telemetry; сам шаг replay этот буфер не заполняет.

curl -sS -X POST "$TAKT_URL/api/predict" \
  -H 'Content-Type: application/json' \
  -d '{
    "tr_id": 131672,
    "T": "2026-01-06T03:35:00Z",
    "target_stop_id": 53700172828,
    "target_time_begin": "2026-01-06T03:50:00Z",
    "cur_dev_s": 274
  }'

Ответ 200 — объект прогноза с source: "api". Он также заменяет текущий результат этого ТС в /api/state. Без подходящей истории возможен числовой результат ML, но уровень будет unknown; один GPS-пакет не заменяет полноценную историю движения.

422 означает неверные поля, будущий момент расчёта или несовпадение цели с плановым окном. При недоступности ML backend возвращает 200 с prediction_s = cur_dev_s, degraded: true, level: "unknown" и пустой вероятностью.

GET/api/riskBackend · риски

Сводка рисков

Готовая сводка для блока «Риск опоздания». Группирует сохранённые прогнозы по tr_id и сортирует группы: high, medium, low, unknown; внутри уровня — по идентификатору. Параметров нет.

curl -sS "$TAKT_URL/api/risk"
{
  "routes": [{
    "tr_id": 131672, "level": "high", "vehicle_count": 1,
    "high_count": 1, "max_late_probability": 0.8,
    "vehicles": [131672]
  }],
  "high_routes": 1,
  "medium_routes": 0,
  "as_of": "2026-01-06T06:35:00+03:00"
}

vehicle_count — размер группы, high_count — число записей high, max_late_probability — максимальная известная оценка в группе или null. vehicles содержит идентификаторы ТС. high_routes и medium_routes считают группы соответствующего уровня. as_of — общие часы потока, которые до старта могут быть null.

Группа здесь соответствует ТС.

В текущем хранилище одна запись на tr_id, поэтому обычно vehicle_count = 1. Название routes не означает, что API знает официальные номера маршрутов.

Сводка не пересчитывает возраст и берёт сохранённые уровни. Кроме того, при наличии числовой вероятности и отсутствии high/medium группа получает low, даже если исходный прогноз был unknown. Для решения о действии проверяйте актуальный level конкретного ТС через /api/state.

GET/api/incidentsBackend · риски

Инциденты и очередь внимания

Выбирает из сохранённых прогнозов только high и medium. Сначала идут high, затем medium; внутри уровня — больший риск раньше. Это текущая очередь внимания, а не история происшествий: записи исчезают, когда прогноз ТС меняется на другой уровень.

curl -sS "$TAKT_URL/api/incidents"

Ответ 200 содержит массив items, его размер total и общие часы as_of. Каждая запись содержит vehicle_id, route_id, level, prediction_s, late_probability, reason, stop_address, source и recommendation. Оба идентификатора в текущем API равны tr_id.

Без данных ответ: {"items":[],"total":0,"as_of":null}. Прогнозы unknown в очередь не входят: пустой список не подтверждает, что все ТС движутся без проблем. Метод также не обновляет давность — сопоставляйте его с /api/state.

POST/api/what-ifBackend · не меняет состояние

Сценарий «что, если»

Без tr_id показывает сводную оценку риска. С tr_id выбирает текущий плановый сегмент выбранного ТС, строит виртуальный путь резерва до целевой остановки и возвращает влияние на основное ТС и резерв. Сценарий не меняет live-поток, не выпускает транспорт и не вызывает ML повторно.

ПолеТип и диапазонПо умолчанию
tr_idinteger > 0 — выбранное ТС/линия для размещения резерванет
extra_vehiclesinteger, от 0 до 20 — дополнительные ТС в общей эвристике0
headway_reduction_pctnumber, от 0 до 50 — сокращение интервала в процентах0
curl -sS -X POST "$TAKT_URL/api/what-if" \
  -H 'Content-Type: application/json' \
  -d '{"extra_vehicles":1,"headway_reduction_pct":0}'

В ответе assumptions повторяет параметры и добавляет risk_multiplier. baseline содержит исходную сводку групп, projected — те же поля плюс projected_late_probability и projected_level. При переданном tr_id добавляются placement с координатами, следующей/целевой остановкой и track, а также affected_vehicles с изменением текущего и прогнозного отклонения.

risk_multiplier = max(0.5, 1 - 0.15 × extra_vehicles - headway_reduction_pct / 100)
projected_late_probability = max_late_probability × risk_multiplier

При одной дополнительной машине множитель равен 0.85: риск 0.8 станет 0.68, то есть medium вместо high. Для null прогноз риска остаётся null, уровень — unknown. Нижняя граница множителя 0.5 ограничивает расчётное снижение 50%.

Это фиксированная эвристика.

Числа не доказывают, что реальный дополнительный автобус снизит риск именно на 15%. Расчёт не исправляет устаревшие данные и наследует ограничения исходной сводки риска. Пустое состояние даёт пустые массивы.

Тело {} допустимо. Значения вне диапазонов возвращают 422.

GET/api/networkBackend · карта

Плановые линии на карте

Отдаёт последовательности координат плановых остановок для отрисовки линий. Не требует телеметрии: геометрия берётся из загруженного расписания. Параметров нет.

curl -sS "$TAKT_URL/api/network"
{
  "kind": "planned_stop_sequences",
  "paths": [{"tr_id":131672,"points":[[37.60,55.75],[37.61,55.76]]}]
}

kind явно обозначает тип геометрии. Каждая запись paths содержит tr_id и до 500 остановок с координатами. Порядок пары — [долгота, широта]. Перед использованием в Leaflet поменяйте его на [lat, lon].

Прямая между остановками не является дорожным маршрутом. API не выполняет прокладку пути по улицам и не возвращает официальный номер маршрута.

POST/api/map-matchBackend · не меняет состояние

Сегмент плановой траектории

Проецирует координату на ближайший отрезок между последовательными плановыми остановками выбранного ТС. Ответ даёт участок, направление и расстояние до следующей остановки по этой прямой. Привязка к дорожному графу не выполняется: для неё нужна утверждённая дорожная геометрия.

Все три поля обязательны: tr_id — целое число больше 0, lon — долгота от −180 до 180, lat — широта от −90 до 90.

curl -sS -X POST "$TAKT_URL/api/map-match" \
  -H 'Content-Type: application/json' \
  -d '{"tr_id":131672,"lon":37.60,"lat":55.75}'
Поле ответа 200Значение
tr_id, stop_id, stop_addressТС и найденная остановка.
segment_start_stop_id, next_stop_idНачальная и следующая остановка ближайшего планового сегмента.
projected_lon, projected_latКоордината проекции на сегмент; distance_m — поперечное расстояние до неё.
distance_to_next_stop_m, direction_degreesРасстояние от проекции до следующей остановки и направление планового сегмента.
road_graph_matchedВсегда false для текущего набора: результат не является дорожным map matching.

При расстоянии 250 м и больше ответ всё ещё может быть 200, но confidence = 0. 404 означает отсутствие геометрии для ТС, 422 — неверные поля запроса.

GET/api/driver-commandsBackend · локальная очередь

Журнал указаний водителю

Возвращает зарегистрированные диспетчером указания: от новых к старым, до 200 последних записей. Без параметров показывает всю очередь; необязательный query-параметр tr_id (целое число) фильтрует её по ТС.

curl -sS "$TAKT_URL/api/driver-commands?tr_id=131672"
{"items":[],"channel":"local_dispatch_outbox","external_delivery":false}

Поля каждой записи описаны в следующем разделе. Пагинации, подтверждения получения и статуса прочтения нет. Очередь находится в памяти и очищается при перезапуске backend. Нечисловой tr_id вернёт 422.

POST/api/driver-commandsBackend · создаёт запись

Создание указания

Регистрирует решение диспетчера для дальнейшей интеграции с каналом связи. Все поля обязательны: role — dispatcher или admin; dispatcher_id — существующий локальный профиль; tr_id — целое число больше 0; action — одно из действий ниже; message — строка от 5 до 300 символов.

actionСмысл
contactСвязаться с водителем и уточнить обстановку.
maintainПродолжать движение по графику.
accelerate_safelyПри возможности безопасно сократить отставание.
slow_down_safelyПри необходимости безопасно снизить темп.
curl -sS -X POST "$TAKT_URL/api/driver-commands" \
  -H 'Content-Type: application/json' \
  -d '{
    "role":"dispatcher",
    "dispatcher_id":"dispatcher-01",
    "tr_id":131672,
    "action":"contact",
    "message":"Уточните причину задержки и текущую обстановку."
  }'
{
  "id": "cmd-1780000000000-1",
  "tr_id": 131672,
  "role": "dispatcher",
  "dispatcher": {"id":"dispatcher-01","name":"Диспетчер №01"},
  "action": "contact",
  "action_title": "Связаться с водителем",
  "message": "Уточните причину задержки и текущую обстановку.",
  "created_at": "2026-05-29T01:26:40+03:00",
  "status": "queued_for_integration",
  "channel": "local_dispatch_outbox",
  "external_delivery": false
}

id — идентификатор записи, created_at — время её создания, action_title — русское название действия. status: "queued_for_integration" означает, что запись добавлена в локальную очередь; channel называет эту очередь.

Водителю ничего не доставлено.

external_delivery: false означает, что радио-, телефонный или телематический канал не подключён. Не показывайте пользователю «отправлено водителю» на основании этого ответа.

Существование tr_id в текущем состоянии не проверяется, но dispatcher_id обязан существовать. Роль берётся из тела запроса. Неверные поля или неизвестный профиль дают 422. Повтор запроса создаёт новую запись — защиты от дублирования нет.

GET/api/admin/emulatorsBackend · источники

Источники и пауза потока

Ответ различает собственный custom-emulator и внешний оригинальный NDTP-образ. В рабочем месте кнопка «Источники данных» и в админке доступны отдельные «Пауза»/«Пуск» для обоих источников. POST /api/admin/emulators/custom-emulator/pause и resume управляют встроенной эмуляцией; для оригинального образа backend меняет его /api/config. При старте и при первом запросе статуса частичный конфиг автоматически восстанавливается до штатных 13 расписанных оригинальных ТС; вместе с 13 custom это максимум 26. units означает настроенные устройства, а waiting_for_live — только отсутствие первого пакета. Для всей картины используйте /api/admin/emulators/all/pause: backend перестаёт принимать новые события.

curl -sS "$TAKT_URL/api/admin/emulators"
curl -sS -X POST "$TAKT_URL/api/admin/emulators/all/pause" \
  -H 'Content-Type: application/json' -d '{"dispatcher_id":"dispatcher-01"}'

Управление доступно любому вошедшему диспетчеру или администратору. Это управляемая пауза, а не удаление контейнера. Для внешнего образа backend сохраняет последний непустой конфиг и восстанавливает его при «Пуск»; на чистом запуске генерирует конфиг 13 расписанных устройств. Жизненный цикл контейнера остаётся в Docker Compose.

GET/api/admin/simulationBackend · симуляция

Состояние симулятора

Помогает подготовить административный тест: сообщает режим, допустимые сценарии и число ТС в текущем состоянии. Запрос без параметров; сам по себе не запускает генерацию событий.

curl -sS "$TAKT_URL/api/admin/simulation"
{
  "role_required":"admin",
  "mode":"live",
  "supported_scenarios":["normal","slow","stop"],
  "active_vehicles":1
}

active_vehicles — размер текущего хранилища прогнозов, включая unknown и устаревшие записи; это не число подключённых устройств. role_required сообщает требуемое значение для следующего POST, но не подтверждает права текущего пользователя.

POST/api/admin/simulationsBackend · асинхронный запуск

Асинхронная симуляция

Основной метод административного контура. Он создаёт запуск в SQLite и сразу отвечает 202 с идентификатором sim-…. Затем фоновая задача меняет status с queued на running, добавляет синтетические события и завершает запуск как completed, cancelled или failed. Точки запуска помечены simulated: true и отображаются на карте отдельной фиолетовой пунктирной линией.

curl -sS -X POST "$TAKT_URL/api/admin/simulations" \
  -H 'Content-Type: application/json' \
  -d '{"dispatcher_id":"admin-01","tr_id":131672,"scenario":"slow","count":5,"interval_s":30}'

Запуск разрешён только профилю с точной ролью Администратор и при mode: "live". normal, slow и stop используют 35, 8 и 0 км/ч. count — от 1 до 20, interval_s — от 5 до 300 секунд.

# История SQLite: фильтр статуса, ТС и ограничение размера
curl -sS "$TAKT_URL/api/admin/simulations?status=completed&tr_id=131672&limit=50"

# Статус и результат одного запуска; доступен и после перезапуска backend
curl -sS "$TAKT_URL/api/admin/simulations/sim-xxxxxxxxxx"

# Отменить активный запуск; остановка произойдёт перед следующим событием
curl -sS -X POST "$TAKT_URL/api/admin/simulations/sim-xxxxxxxxxx/cancel" \
  -H 'Content-Type: application/json' -d '{"dispatcher_id":"admin-01"}'

Объект запуска содержит operator, progress с completed/total, массив events и effect с прогнозом, вероятностью и уровнем до/после. История читается из SQLite и переживает перезапуск. Ошибки: 403 — не администратор, 409 — выбран replay, повторная отмена или запуск уже от предыдущего процесса, 404 — неизвестный id при чтении.

POST/api/admin/simulationBackend · legacy

Legacy-симуляция

Создаёт небольшую последовательность синтетических событий и пропускает её через живой обработчик телеметрии. Используйте для проверки отображения и обработки данных. Сначала осознанно переключите backend в live; выбор режима очищает текущую историю.

ПолеПравило
roleОбязательная строка admin. Другая роль даёт 403.
tr_idОбязательное целое число > 0. Для ТС должны находиться координаты в состоянии или расписании.
scenarionormal — 35 км/ч, slow — 8 км/ч, stop — 0 км/ч. По умолчанию slow.
countЦелое число от 1 до 20. По умолчанию 3 события.
interval_sЦелое число от 5 до 300. По умолчанию 30 секунд между событиями.
curl -sS -X POST "$TAKT_URL/api/admin/simulation" \
  -H 'Content-Type: application/json' \
  -d '{"role":"admin","tr_id":131672,"scenario":"slow","count":3,"interval_s":30}'
{
  "accepted":3,
  "scenario":"slow",
  "tr_id":131672,
  "role":"admin",
  "message":"Simulation events injected into live pipeline"
}

События создаются в недавнем прошлом: первое — примерно count × interval_s секунд назад, последнее — interval_s секунд назад. Координаты берутся из состояния или плана и немного смещаются на каждом шаге, даже в сценарии stop. Это тестовый генератор, не физическая модель движения по маршруту.

accepted считает попытки обработки. Если уже принята более свежая телеметрия, синтетические события могут быть пропущены как опоздавшие. Результат смотрите в /api/state; наличие прогноза и высокого риска не гарантируется.

403 — role не admin; 409 — выбран replay; 404 — для ТС нет координат; 422 — неверные поля. В отличие от what-if, этот метод действительно меняет историю и может изменить прогнозы.

GET/api/metricsBackend · качество модели

Офлайн-метрики модели

Возвращает результаты оценки на сохранённой тестовой выборке и важность признаков. Используйте для блока «Надёжность прогноза». Метод не сравнивает текущие live-прогнозы с реальными прибытиями и не пересчитывает качество на лету.

curl -sS "$TAKT_URL/api/metrics"
Блок или полеЧто означает
v5.model, v5.version, v5.target_modeСтабильное имя API-контракта и версия расчёта. В поставке: v5, champion-b4b и direct_delay; итог — один воспроизводимый CatBoost-чемпион.
v5.leaderboard_scoreФактически полученный score платформы для сохранённого submission. Это нормированная скрытая метрика, а не локальный MAE.
v5.mae_sСредняя абсолютная ошибка прогноза в секундах. Меньше — лучше; это средняя величина, не максимальная ошибка отдельного рейса.
v5.baseline_mae_sОшибка подхода «будущее отклонение равно текущему», без ML.
v5.improvement_pct100 × (1 - mae_s / baseline_mae_s). Поле появляется, если обе оценки пригодны для расчёта.
v5.interval_radius_s, v5.late_threshold_sРадиус интервала из метаданных и порог опоздания, по умолчанию 120 с.
v5.coverage, v5.batch_inference_msПокрытие интервала и измерение пакетного инференса из актуального отчёта; это оценка на выданной test-части, а не гарантия live-задержки.
feature_importanceДо шести наиболее важных признаков из артефакта V5: feature и importance. Глобальная важность для модели, не объяснение конкретного прогноза.
readableГотовые строки mae, baseline, coverage для интерфейса. Для вычислений используйте числовые поля.
Верхнеуровневые метрикиmae_test, interval_coverage, real_vehicle_group_holdout и остальные поля содержат полный офлайн-отчёт. Краткое представление находится в v5.

Для поставляемых артефактов MAE на 353 выданных test-точках составляет 62.09 с против 93.36 с у persistence-baseline (улучшение 33.49%). 5-fold holdout по реальным ТС даёт 80.24 с и лучше показывает ограничение переноса. Submission из reference-коммита b4b636b получил сообщённый score платформы 1.00000. Данные относятся к одному дню, поэтому эта оценка не подтверждает качество на будущих днях.

Текущую длительность обращения к ML смотрите в /api/state → counters.last_inference_ms. Она включает HTTP-вызов и отличается от офлайн-времени пакетного инференса.

Внутренний сервис · порт 8001

Отдельный ML API

ML-сервис рассчитывает champion-b4b по тем же 60 причинным признакам, что и офлайн-пайплайн, и не хранит состояние транспорта. Итоговый прогноз — прямой ответ одного воспроизводимого CatBoost-чемпиона. Обычной интеграции достаточно backend: он выбирает цель, готовит историю, оценивает свежесть и обеспечивает fallback.

Без Docker его Swagger находится по адресу http://127.0.0.1:8001/docs, схема — /openapi.json на том же порту. В Docker обращайтесь из сети Compose к http://ml:8001: запрос /predict_v5 на backend-порту не проксируется в ML.

GET /health

Ответ {"status":"ok","model":"v5"} сообщает стабильное имя API-контракта; версия и режим цели доступны в офлайн-метриках. Этот метод не выполняет тестовый прогноз.

POST /predict_v5

Основной метод инференса. Принимает три массива одинаковой длины — от 1 до 512 элементов каждый. Для каждой точки требуется строгий горизонт 600 < horizon_s <= 900; результаты возвращаются в том же порядке и уже содержат полное отклонение (остаток плюс текущее cur_dev_s).

МассивСодержимое одного элемента
pointsОбъект точки: tr_id, T, target_stop_id, target_time_begin, cur_dev_s.
historiesМассив событий этого ТС: tr_id, event_time, location_valid, lon, lat, speed. Необязательные alt и heading заменяются на 0 при отсутствии. Пустая история допускается технически.
schedulesМассив плановых остановок: tr_id, tt_action_item_id, time_begin и геометрия geom в формате POINT (lon lat) либо отдельные lon, lat. Нужны целевая и окружающие остановки; backend передаёт окно ±30 минут от T.

Следующий компактный пример иллюстрирует формат на одной точке и одном событии. Для содержательного прогноза передавайте полную доступную историю и плановый контекст.

curl -sS -X POST http://127.0.0.1:8001/predict_v5 \
  -H 'Content-Type: application/json' \
  -d '{
    "points":[{
      "tr_id":131672,"T":"2026-01-06T03:35:00Z",
      "target_stop_id":53700172828,
      "target_time_begin":"2026-01-06T03:50:00Z","cur_dev_s":274
    }],
    "histories":[[{
      "tr_id":131672,"event_time":"2026-01-06T03:34:50Z",
      "location_valid":true,"lon":37.60,"lat":55.75,"speed":25
    }]],
    "schedules":[[{
      "tr_id":131672,"tt_action_item_id":53700172828,
      "time_begin":"2026-01-06T03:50:00Z",
      "lon":37.61,"lat":55.76
    }]]
  }'
{"predictions":[{"prediction_s":180.0,"model":"v5"}]}

ML возвращает только отклонение и имя модели. Он не добавляет level, вероятность, интервал, координаты или признаки деградации — это делает backend. Неверные размеры массивов дают 422. Вложенные объекты описаны как свободные словари: отсутствующие поля и неподходящие данные могут привести к 500, поскольку полный контракт внутри ML пока не валидируется. Проверка первой остановки в окне выполняется в backend.

POST /predict — legacy

Прежний метод принимает {"rows":[{…}]}: от 1 до 512 объектов с 15 числовыми полями диагностических признаков. Все поля обязательны; дополнительные поля и нечисловые значения запрещены. При совместимой legacy-модели ответ содержит predictions с отклонением, интервалом, вероятностью и именем модели.

Для поставляемой модели используйте /predict_v5.

Схема legacy-запроса содержит 15 признаков, а рабочая модель строит 60 признаков из сырой точки, истории и расписания. Поэтому legacy endpoint явно отвечает 410; Backend использует новый метод.

Ошибки и диагностика

Сначала проверяйте HTTP-статус, затем содержимое ответа. Успешный HTTP-запрос к прогнозу ещё не означает, что ML доступен или данные пригодны: для этого есть degraded, stale и level.

СтатусПочему возникаетЧто сделать
200Запрос обработан; прогноз может быть резервным.Проверить поля качества и причину unknown.
201Создана запись локального указания.Сохранить id. Не считать это доставкой водителю.
403Симуляция вызвана с ролью, отличной от admin.Для административного теста передать role=admin. Это локальная проверка значения.
404Неизвестный путь или нет плановой геометрии/координат для ТС.Проверить порт сервиса, путь и наличие tr_id в расписании.
409Метод несовместим с режимом: replay в live или симуляция в replay.Прочитать /api/state. Переключать режим только с учётом сброса.
422Неверная структура, диапазон, дата или прогнозная цель.Изучить detail, исправить запрос и сверить цель с планом.
500Необработанная ошибка: например, неполные вложенные данные прямого ML-запроса или повреждённые артефакты.Проверить входные данные и логи backend/ML.
502 / 504Возможная ошибка прокси nginx при недоступном или не ответившем вовремя backend.Проверить /health напрямую на порту 8000 и логи контейнера.

Два формата detail

Ошибки бизнес-проверок обычно содержат строку; ошибки валидации FastAPI — массив с расположением поля и пояснением. Не предполагайте, что detail всегда одного типа. Ошибки прокси и необработанные 500 могут вообще не быть JSON.

{"detail":"Switch to replay mode first"}
{
  "detail": [{
    "type":"greater_than",
    "loc":["body",0,"tr_id"],
    "msg":"Input should be greater than 0",
    "input":0,
    "ctx":{"gt":0}
  }]
}

В этом примере loc указывает на поле tr_id первого события в массиве тела запроса.

async function readState() {
  const response = await fetch('/api/state');
  if (!response.ok) {
    const details = await response.text();
    throw new Error(`HTTP ${response.status}: ${details}`);
  }
  return response.json();
}

try {
  const { vehicles } = await readState();
  console.log(vehicles.map(describePrediction));
} catch (error) {
  console.error('Не удалось получить состояние:', error.message);
}

Функция describePrediction приведена в разделе «Как читать результат». Для запуска примера используйте JavaScript-модуль или консоль браузера на странице Такт.

Частые вопросы

НаблюдениеОбъяснение и следующий шаг
После запуска vehicles пустВ replay выполните шаг. В live проверьте приход событий, сопоставление unit_id → tr_id и выбранный режим.
accepted растёт, а прогноз не меняетсяПроверьте mode, порядок event_time, счётчик дубликатов и 30-секундное ограничение расчёта на ТС.
«Нет плановой остановки…»В текущем плане нет остановки в (T+10, T+15] минут. Сверьте ТС, время, часовой пояс и расписание. Map-match ищет ближайшую координату, а не подходящее время.
«Нет подтверждённого текущего отклонения»Live ещё не наблюдал ТС возле остановки в условиях привязки. Случайные координаты эмулятора не подтверждают прибытие.
degraded=trueBackend использовал текущее отклонение вместо ML. Проверьте доступность ML, его логи и адрес ML_URL.
state показывает unknown, а risk — low/highСводка риска использует сохранённые данные и собственную группировку; state обновляет давность. Для решения по конкретному ТС используйте state.
Время отличается на три часаUTC переводится в Europe/Moscow. Передавайте явный часовой пояс, не прибавляйте смещение вручную.
Указание есть в журнале, но водитель его не получилВ текущем MVP подключена только локальная очередь. Внешняя доставка не реализована.

Границы прототипа и дополнительные материалы

Телеметрические буферы, текущие прогнозы и очередь указаний работают в памяти одного backend-процесса. Профили диспетчеров, назначения и запуски симуляций сохраняются в локальной SQLite. Здесь нет гарантированной внешней доставки, синхронизации нескольких backend-воркеров или полноценной аутентификации. Историческое качество модели, эвристический риск и сценарный коэффициент не заменяют проверку на реальном потоке.
